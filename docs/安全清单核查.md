# 安全清单核查（开发文档 §10.3）

> 核查方式：**自动化检查 + 可复现的命令行证据**，并经过一轮独立对抗性验证（见 `docs/交付验收报告.md` §5）。每一项都给出命令与其真实输出摘要，
> 便于人工复核。结论：清单 9 项全部满足（第 8 项的“入口层”表述已按实测更正）；另记录 4 项风险：
> R-1 附件目录暴露（已给出安全默认）、R-2 邮件风暴防护、R-3 附件预览存储型 XSS（**独立验证发现，已修复**）、
> R-4 配置缓存陈旧窗口（已记录并加固）。

## 0. 自动化闸门

```bash
cd /srv/ticket-system/app
.venv/bin/python manage.py check                 # → System check identified no issues (0 silenced).
.venv/bin/python manage.py makemigrations --check --dry-run   # → No changes detected
.venv/bin/ruff check .                           # → All checks passed!
.venv/bin/python -m pytest                       # → 402 passed

# 生产安全自检（模拟生产环境变量；SECRET_KEY 用 ≥50 位随机串）
DJANGO_SECRET_KEY="$(openssl rand -base64 48)" DJANGO_ALLOWED_HOSTS=ticket.example.com \
  DJANGO_SECURE_SSL_REDIRECT=True .venv/bin/python manage.py check --deploy
# → 仅剩 security.W021（HSTS preload），见下方说明
```

`check --deploy` 结果说明（均已实测）：

| 设置 | 结果 |
|---|---|
| 本地开发 `.env`（`DJANGO_SECURE_SSL_REDIRECT=False`） | `W008`（SSL 重定向）——为本地 HTTP 调试刻意关闭 |
| 生产（`DJANGO_SECURE_SSL_REDIRECT=True`，≥50 位随机 `SECRET_KEY`） | 仅剩 `W021`（HSTS preload） |
| 再设 `DJANGO_SECURE_HSTS_PRELOAD=True` | **0 issues** |

`W021` 是**有意保留**：HSTS preload 一旦提交浏览器列表就很难撤回（需要长期保持 HTTPS 且无法快速下线），
建议域名稳定运行一段时间、确认证书自动续期无误后再打开。其余安全项（`SECURE_HSTS_SECONDS`、
`SECURE_HSTS_INCLUDE_SUBDOMAINS`、`SESSION_COOKIE_SECURE`、`CSRF_COOKIE_SECURE`、`X_FRAME_OPTIONS=DENY`、
`SECURE_CONTENT_TYPE_NOSNIFF`、`SECURE_REFERRER_POLICY`、`SECURE_PROXY_SSL_HEADER`）在生产模式下默认开启。

CI 对应配置见 `.github/workflows/ci.yml`（含 MariaDB 集成测试作业；该作业注入真实长度的密钥，`check --deploy` 同样通过）。

## 2. `SECRET_KEY` 与 `FERNET_KEY` 来自环境变量，未硬编码

```text
config/settings.py:61  SECRET_KEY = env("DJANGO_SECRET_KEY")
config/settings.py:63-68  未设置时：DEBUG/测试环境用开发占位值，否则抛 ImproperlyConfigured
```

  `SECRET_KEY`/`FERNET_KEY` 会退化为确定性派生值，以便"没有 `.env` 也能跑起来/跑测试"。
- `.env` 已被 `.gitignore` 与 `.dockerignore` 双重排除；`.env.example` 全部是占位文本（`请替换` / `CHANGE_ME`）。
- `docker/entrypoint.sh` 额外拦截：密钥仍是 `.env.example` 的占位值时拒绝启动（`check_env()`）。
- 邮箱授权码用 Fernet 加密存 `BinaryField`（`apps/core/crypto.py`），并有测试断言密文中不含明文：

## 需在部署时显式确认的风险

### R-1 附件目录的对外暴露（已提供默认安全方案）

`/media/attachments/` 若由 Nginx 直出且无鉴权，任何人拿到 URL 即可绕过工单可见性下载附件
（路径含自增 `ticket_id`，枚举成本低）。**当前配置已改为安全默认**：

1. 应用层视图 `apps/tickets/views.py::_serve_attachment` 在鉴权通过后返回
   `X-Accel-Redirect: /media/attachments/<百分号编码路径>`（需在 `.env` 设置
   `ATTACHMENT_X_ACCEL_PREFIX=/media/attachments/`）；
2. `deploy/nginx/ticket.example.com.conf` 中该 location 已设为 `internal;`，匿名直链一律 404；
3. 未设置该环境变量时 Django 自行流式返回文件（功能可用，但会占用 web 进程带宽）。

`/media/`（attachments 之外）仍为直出，仅用于富文本内嵌图片，请勿存放敏感文件。

**配置不变量（务必对齐，否则附件 404）**：

```text
X-Accel-Redirect 的值 = ATTACHMENT_X_ACCEL_PREFIX + <数据库 attachments.path>
attachments.path 形如        attachments/{ticket_id}/{message_key}/{filename}
例如                          /media/attachments/attachments/12/msg-abc/报告.pdf
Nginx location               ^~ /media/attachments/  →  alias /srv/ticket-system/media/
                             （alias 指向媒体根目录，因为 URI 里已含一层 attachments/）
磁盘真实文件                  /srv/ticket-system/media/attachments/12/msg-abc/报告.pdf
```

回归保护：`tests/test_ticket_views.py::test_attachment_download_uses_x_accel_when_configured`、
`tests/test_attachment_security.py::test_x_accel_uri_maps_to_real_file_through_nginx_alias`
（按 Nginx `alias` 规则换算后必须等于磁盘真实文件），以及
`test_nginx_config_keeps_attachments_internal`（**配置漂移守卫**：一旦有人把该 location 改回直出、
或把 `alias` 指回 `media/attachments/`，用例立即失败）。

### R-3 附件内联预览的存储型 XSS（独立验证发现，已修复）

**问题**：`_serve_attachment` 原先直接把发件人可控的 `Content-Type` 用于内联响应，且预览闸门只看
`is_dangerous`（10 个可执行扩展名）。外部发件人只要发一个 `report.html` / `image.svg` /
`report.xhtml` 附件，客服点击"预览"就会在应用同源执行其中的脚本（可读取非 HttpOnly 的
`csrftoken`、以受害者身份发同源请求）。

**修复**（`apps/tickets/models.py` + `apps/tickets/views.py` + `templates/tickets/_timeline.html`）：

1. `Attachment.normalized_filename` 先剥离控制字符与**尾部空格/点**——`tool.exe.`、`tool.exe `
   在 Windows/浏览器保存时会变成 `tool.exe`，不规范化即可绕过危险扩展名判断；
2. 新增 `is_previewable`：**只允许白名单类型**内联预览
   （`image/png|jpeg|gif|webp|bmp`、`text/plain`、`application/pdf`）；
   HTML/SVG/XHTML/XML 等活动内容与一切未知类型只能下载（HTTP 403）；
3. 预览响应使用**白名单 MIME**（而不是原始 MIME），并强制
   `X-Content-Type-Options: nosniff` + `Content-Security-Policy: default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; sandbox`，
   即使把 HTML 伪装成 `image/png` 也不会被浏览器按 HTML 解析；
4. 时间线模板只对 `is_previewable` 的附件显示"预览"按钮，其余显示"不可预览"。

回归保护：`tests/test_attachment_security.py`（42 例：扩展名规范化 11 组、活动内容禁止预览 10 组、
白名单类型与响应头 6 组、X-Accel/Nginx 契约 3 组）。

### R-4 配置缓存的陈旧窗口（已记录）

`Setting` 使用 30 秒 TTL 的 LocMemCache，且每个进程各有一份；`Setting.set()` 会失效本进程缓存并写审计，
但 `QuerySet.update()` 不触发 `save()`/信号，**不会**失效缓存。因此：

- 应用代码一律使用 `Setting.set()` / `Setting.bulk_set()`（`bulk_set` 为本次新增）；
- 多进程部署下，配置修改最长 30 秒内在其他进程生效，属可接受折衷；
- 测试侧已在根 `conftest.py` 用 autouse fixture 逐用例 `cache.clear()`，避免跨用例污染。

### R-2 邮件风暴防护依赖"防循环过滤 + 自动回复防重复"

- 单封来信最多触发一条自动回复；自动回复带 `Auto-Submitted: auto-replied`，
  再次入站会被 `filters.is_loop_mail` 丢弃（对称防护，`apps/mailboxes/tests/test_filters.py` 覆盖）。
- 同发件人 N 小时内只发一次（`Setting.first_contact_window_hours`，默认 24）。
- 建议上线后按 `docs/运维手册.md` 的"出站风暴预警阈值"监控 SMTP 发信量，
  一旦异常可用"冻结邮箱 `is_active=0` → 排查 → 再启用"的应急流程。
