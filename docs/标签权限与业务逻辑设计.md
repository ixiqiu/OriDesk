# 工单标签：权限与业务逻辑设计（v1.2）

> 背景：开发文档 §4.4 的 `Rule.ACTION_TYPE_CHOICES` 定义了 `add_tag`（打标签），但 §4.3 的模型没有标签载体。
> 按 §10.4「新增模型需人工确认」，经确认后新增 `Tag` / `TicketTag` 两个模型（迁移 `tickets/0002_*`）。
> 本文件把"标签能怎么用、谁能用、边界在哪"写成可执行的规则，作为实现与测试的共同依据。

---

## 1. 数据模型与作用域

```text
Tag（tags）                          TicketTag（ticket_tags）
├── name        标签名（≤50）        ├── ticket    → Ticket（CASCADE）
├── group       → Group 或 NULL      ├── tag       → Tag（CASCADE）
│                 NULL = 全局标签    ├── added_by  → User 或 NULL（规则打标签时为空）
│                 非空 = 该组专属    ├── source    rule / manual
├── color       7 种预设配色         └── created_at
├── description 说明（≤200）
├── is_active   启用开关             唯一约束：unique_ticket_tag(ticket, tag)
└── created_at                       索引/排序：tag__name, id
   唯一约束：unique_tag_per_group(group, name)
```

**作用域语义（核心）**

| 标签类型 | 谁能看到 | 谁能在自己组的工单上使用 | 典型用途 |
|---|---|---|---|
| 全局标签（`group = NULL`） | 所有人 | 所有组 | 「紧急」「待客户确认」这类跨组一致的状态 |
| 组专属标签（`group = X`） | 所有人可见其存在（标签总览页） | 仅 X 组 | 「发票」「合同」这类只有本组业务含义的分类 |

**两条不变量（模型层保证，§10.1 模型先行）**

1. **作用域内同名唯一**：`(group, name)` 唯一。注意 SQL 中 `NULL` 互不相等，所以"全局标签同名"这一半
   必须由 `Tag.clean()/save()` 兜底——与 `Mailbox` 的"全局唯一兜底邮箱"是同一类处理（见 DEV-4）。
   名称比较统一走 `iexact`，与 MariaDB `utf8mb4_unicode_ci`（大小写不敏感）保持一致；
   否则生产库上 `Urgent` / `urgent` 会撞唯一约束而抛 `IntegrityError`（表现为 500 而非表单错误）。
2. **同一工单同一标签唯一**：`unique_ticket_tag(ticket, tag)`，打标签天然幂等。

**名称规范化**：去首尾空白 + 压缩内部连续空白（`Tag.normalize_name`）。空名一律拒绝。
中文、emoji、空格均可；不做大小写强制转换（保留展示形态，只把"判重"变成大小写不敏感）。

## 2. 权限矩阵

角色定义取自现有权限模型（`apps/accounts/models.py`）：
`超管` = `is_superadmin`；`组管理员` = `UserGroup.is_admin=True`；`管理员组成员` = 所属组的 `is_admin_group=True`；
`组员` = 普通 `UserGroup` 成员；`可见` = `apps/tickets/selectors.visible_tickets()` 能查到该工单（§5.6）。

### 2.1 标签字典维护（`/routing/tags/`）

| 操作 | 超管 | 管理员组成员 | 组管理员 | 组员 | 未登录 |
|---|---|---|---|---|---|
| 查看标签总览 `/tags/` | ✅ | ✅ | ✅ | ✅ | ❌ 跳登录 |
| 新建 / 编辑 / 停用 / 删除标签 | ✅ | ✅ | ✅ | ❌ 403 | ❌ |
| Django Admin 操作 | ✅(staff) | ❌ | ❌ | ❌ | ❌ |

实现：视图一律 `@routing_manager_required`（= 超管 ∨ 管理员组成员 ∨ 组管理员，`apps/core/permissions.py`）。
理由：标签是**路由与自动化的字典**，与规则/模板同级，不能由任意组员改；但独立标签字典的维护权
不应只给超管，否则每个新标签都要找超管（§2.7 的精神是权限分层而非单点）。

### 2.2 工单打标签 / 移除标签（`/tickets/<pk>/tags/…`）

| 操作 | 超管 | 管理员组成员 | 组管理员 | 工单所属组组员 | 其他组组员 |
|---|---|---|---|---|---|
| 查看工单上的标签 | ✅ | ✅ | ✅ | ✅ | ❌（工单本身不可见 → 404） |
| 打标签（全局标签） | ✅ | ✅ | ✅ | ✅ | ❌ |
| 打标签（本组专属标签） | ✅ | ✅ | ✅ | ✅ | ❌ |
| 打标签（**其他组**专属标签） | ❌ | ❌ | ❌ | ❌ | ❌ |
| 移除标签（含规则打的） | ✅ | ✅ | ✅ | ✅ | ❌ |

实现要点：

- 视图先 `get_visible_ticket(user, pk)`，不可见直接 404（不泄露存在性）；
- 服务层 `add_tag()` 再做一次**作用域校验**（`Tag.is_available_for(ticket.group)`）——
  界面下拉只是体验，服务层才是闸门：把别的组的专属标签打到本工单会被拒绝；
- 可打标签范围 = `tags_available_for(ticket.group)` = 全局标签 + 本组标签 ∩ 启用中；
- 写操作一律 POST + CSRF，成功后 `messages` + PRG。
- **为什么组员也能打/移标签**：§2.6 的组内协作是"低仪式感、共享可见"（认领都是可选的），
  标签是协作分类而非权限动作；真正的权限动作（改派、状态、删标签字典）才收紧。

### 2.3 规则自动打标签（`add_tag` 动作）

| 项 | 规则 |
|---|---|
| 触发时机 | 仅**新建工单**时（`pipeline` 中 `created=True` 分支），与 `set_status` / `assign_user` 一致 |
| 命中规则数 | §2.2「第一个命中即停」：只执行**第一条命中规则**的动作 |
| 标签作用域 | 落库到**该工单所属组**的作用域；若同名全局标签已存在则复用全局标签 |
| 自动创建 | 允许。规则里的标签名若不存在会自动创建（管理员配置规则即授权），并写审计 |
| `added_by` | 空（系统行为），`source="rule"` 与人工打标签区分 |
| 审计 | 与同一次规则执行合并为**一条** `rule_action` 审计（`detail.applied=["tag=合同"]`），
  重复命中记为 `tag=合同(已存在)`，不产生重复关联 |
| 标签已停用 | 跳过并记 `WARNING`（不因为一个停用标签中断规则执行） |
| 标签名空 | 跳过并记 `WARNING` |

**重要边界（DEV-17）**：`add_tag` / `set_status` 不决定归属组。若某条优先级最高的规则命中了却解析不出组，
路由引擎**继续尝试下一条规则**，而不是失败——否则"只打标签"的规则会让所有来信无法建单。

### 3.1 生命周期与边界

- **停用 vs 删除**：正常"退役"用 `is_active=False`（历史工单上的标签继续显示，下拉不再出现）；
  **删除**是不可逆的，会级联移除所有工单上的该标签，界面必须二次确认并显示影响面。
  设计上推荐默认停用，删除只用于"建错了"。
- **改派（§2.2）**：标签随工单走，不删除（保留历史事实）。原组专属标签对新组不再可用，
  通过 `TicketTag.is_foreign` 在界面上弱化标注为历史标签——这比"改派时静默删标签"更可追溯。
- **标签 ≠ 待回复**：`is_awaiting_reply` 是**一等状态字段**（客户来信置真、人工回复置假，驱动协作），
  不要用标签去模拟它；因此建议标签字典中不建名为「待回复」的标签（语义重复会产生两个真相来源）。
- **工单合并**：同一客户的多封来信归并到同一工单，标签自然保留在工单上，不重复累加。
- **并发**：两个 worker 同时打同一标签时，`get_or_create` 的竞争由唯一约束兜底（捕获 `IntegrityError` 后回查）。

## 4. 与其它模块的边界

| 模块 | 交互 |
|---|---|
| 路由引擎 | 标签**不参与**归属组决策；`add_tag` 规则的命中不阻断后续规则的路由尝试（DEV-17） |
| 可见性（§5.6） | 标签不改变可见性：工单可见性仍只看归属组与用户身份；标签筛选在可见集合内做二次过滤 |
| 审计 | 人工标签变更为 `config_change` + `detail.event=tag_added/tag_removed`；规则打标签并入 `rule_action` |
| 邮件 | 标签只存在于系统内部，**不出现在对外邮件的主题/正文/头里**（不泄露内部协作信息） |
| 待回复标签 | 见 3.1：`is_awaiting_reply` 独立存在，标签系统不接管 |
| Django Admin | `Tag` / `TicketTag` 已注册；`TicketAdmin` 内联显示工单标签，便于运维排查 |

## 7. 场景走查（把规则串起来看）

**场景 1：规则自动打标签（无需人工介入）**

```text
客户来信「紧急：系统不可用」
  → 防循环过滤通过 → 归并失败 → 按规则路由
  → 命中规则「主题含紧急 → 打标签：紧急」（该规则不决定归属组）
      · 路由引擎继续找能定组的规则 / 兜底组 → 技术支持组
      · 工单创建后执行规则动作：Tag(紧急, 全局) 复用或新建 → TicketTag(source=rule, added_by=NULL)
      · 审计：一条 rule_action{applied:["tag=紧急"]}
  → 打待回复标签 → 首次进线自动回复（失败也只记日志，不影响工单与标签）
结果：工单归属技术支持组，带「紧急」标签，组内任何人都能在收件箱按「紧急」筛选到它。
```

**场景 2：人工补标签 + 协作筛选**

```text
技术支持组组员 tech1 打开工单 → 标签区下拉（全局标签 + 技术支持组标签）
  → 选「待客户确认」（已有）或输入「等客户回电」（自动在该组作用域新建）
  → POST /tickets/<pk>/tags/add/ → 幂等写入 + 审计 tag_added
  → 收件箱 ?tag=<id> 只看带该标签的工单；导航/列表角标显示标签
任何人（含跨组管理员）都能移除标签 —— 移除同样写审计 tag_removed。
```

**场景 3：改派后的标签归属**

```text
工单原属技术支持组，带标签「技术专属」（tech 组专属）与「紧急」（全局）
  → 改派到财务组
      · ticket.group 变为财务组，标签一条都不删（历史事实保留）
      · 「技术专属」变成历史标签（is_foreign=True）：界面弱化显示，且不再出现在可选下拉
      · 「紧急」是全局标签，继续正常可用
      · 财务组组员看到「技术专属」时会明白"这是上一手留下的"，而不是以为标签丢了
```

**场景 4：标签退役**

```text
业务不再需要「旧分类」
  → 首选：停用（is_active=False）——历史工单仍显示，新的打标签下拉里消失，可随时恢复
  → 例外：建错了才删除——删除会级联清空所有工单上的该标签，界面必须二次确认并给出影响工单数
```

**场景 5：跨组管理员**

```text
管理员组成员（可跨组查看）打开财务组工单 → 可打「全局标签」+「财务组标签」
  · 不能打技术支持组的专属标签（服务层拒绝并提示"属于用户组「技术支持组」"）
  · 管理员不能通过标签把工单"变成"自己的组——归属组只由改派动作决定
```

## 8. 数据库与查询注意点

| 项 | 说明 |
|---|---|
| 表与字符集 | `tags`、`ticket_tags` 随库使用 utf8mb4；`name` 索引键 50×4=200 字节，远低于限制，无 §8.1 的索引长度问题 |
| 唯一约束 | `unique_tag_per_group(group, name)` 在 MariaDB 上对**非空 group** 生效；全局标签同名由 `clean()/save()` 兜底（同 DEV-4 的处理方式） |
| 级联 | `TicketTag.ticket` / `TicketTag.tag` 均为 `CASCADE`：删工单或删标签都会自动清理关联；`added_by` 为 `SET_NULL`，用户离职不丢标签记录 |
| 常用查询 | 工单标签：`ticket.ticket_tags.select_related("tag")`；按标签筛：`.filter(ticket_tags__tag_id=…)`（需 `distinct()` 去重）；标签用量：`tag.ticket_tags.count()` |
| 巡检 SQL | 作用域内重复标签检测（正常应返回 0 行）：<br>`SELECT group_id, LOWER(name), COUNT(*) FROM tags GROUP BY group_id, LOWER(name) HAVING COUNT(*)>1;` |
| 容量 | 标签是低频写、高频读的小表；单工单上限 20，单组标签量级预计在几十条，无需额外缓存 |
