# 移动端推送部署指南 · OriDesk Android

配套：`docs/部署手册.md`（后端主体部署）、`ixiqiu/OriDesk-Android` 仓库（安卓工程与 APK）。
本文所有命令中的 `/srv/ticket-system/app` 为项目目录、`ticket.example.com` 为后端域名、
`ntfy.example.com` 为 ntfy 域名，请按实际环境替换。

---

## 0. 先理解链路，再动手

推送不是"配一个地址就通"的东西，它由**三段**串成，任何一段断了现象都一样（收不到通知），
但排查位置完全不同：

```
收信流水线           后端                        ntfy 实例                 手机
─────────►  受众解析/聚合  ──HTTPS POST──►  按 topic 存/转发  ──长连接──►  App 订阅 /<topic>/json
 (IMAP 轮询)   发布到 topic                    缓存 12h              自己弹通知
```

| 段 | 谁负责 | 断了的典型现象 |
|---|---|---|
| 后端 → ntfy | `ntfy_enabled` / `ntfy_server_url` / `ntfy_token` 三项配置 | 后端日志出现 `ntfy 发布失败` |
| 手机 → ntfy | App 里的订阅令牌 + **手机能访问到** ntfy 地址 | 后端显示发布成功，手机静默无反应 |
| 收信 → 后端 | 事件钩子（自动，无需配置） | 有信进系统但没有任何通知 |

**排查口诀：先看后端日志有没有"发布成功"，再看手机能不能直接打开 ntfy 地址。**
两端都通、中间不通，一定是反代或令牌的问题。

## 1. 前置条件

| # | 项 | 要求 |
|---|---|---|
| 1 | 后端版本 | 已包含 `apps/notifications/`（提交 `40d8f09` 之后） |
| 2 | 域名 | ntfy 需要一个**手机能访问到**的域名（可与后端同域不同子域） |
| 3 | 证书 | ntfy 必须 HTTPS。客户端 `usesCleartextTraffic=false`，**http 连不上** |
| 4 | 端口 | ntfy 容器端口只绑本机（compose 已默认 `127.0.0.1:2586`），外部走 Nginx |
| 5 | 反代 | 宿主机 Nginx |

> **为什么 ntfy 必须独立域名而不是挂在后端域名的子路径下**：ntfy 的 `base-url` 与
> WebSocket/长连接路径在子路径下容易出错。用子域最省事
> （`ntfy.example.com` → 本机 `127.0.0.1:2586`）。

## 2. 启动 ntfy 服务

`docker-compose.yml` 已包含 ntfy 服务（镜像钉在 `v2.28.0`）与 `ntfy_data` 数据卷。

```bash
cd /srv/ticket-system/app
git pull
docker compose up -d --build

# 确认起来了
docker compose ps ntfy
curl -fsS http://127.0.0.1:2586/v1/health
# 期望：{"healthy":true}
```

compose 里已设的关键项（**不要随意改**）：

| 环境变量 | 值 | 为什么 |
|---|---|---|
| `NTFY_BEHIND_PROXY` | `true` | 不设的话反代后面**所有手机被当成同一个 IP** 共用一个限流桶，几台设备就能互相把对方限流掉，且极难排查 |
| `NTFY_CACHE_FILE` | `/var/lib/ntfy/cache.db` | 消息缓存 12h。**断线补齐全靠它** —— 这是选 ntfy 而非裸 WebSocket 的主要收益 |
| `NTFY_AUTH_DEFAULT_ACCESS` | `deny-all` | 未在 ACL 中放行的一律拒绝。"topic 是密码"之外的纵深防御 |
| `NTFY_BASE_URL` | 见下 | 必须与手机访问的地址一致，否则 ntfy 生成的自引用链接会指错 |

若 ntfy 对外域名不是默认值，在 `.env` 里加：

```bash
NTFY_BASE_URL=https://ntfy.example.com
NTFY_PORT=2586
```

改完 `docker compose up -d ntfy` 重建即可。

## 3. 建用户与令牌（**最小权限**，别偷懒）

ntfy 默认 `deny-all`，不建用户什么都没法收发。

```bash
# 1) 发布方：后端用。需要读写权限（要发布），给 admin 角色最省事
docker compose exec ntfy ntfy user add --role=admin oridesk
docker compose exec ntfy ntfy token add --label=backend oridesk
#    记下输出的 tk_…，形如 tk_AgQdq7mVBoFD37zQVN29RhuMzNIz2

# 2) 订阅方：手机用。**只读**，且只能读 oridesk- 前缀的 topic
docker compose exec ntfy ntfy user add phone
docker compose exec ntfy ntfy access phone "oridesk-*" read-only
docker compose exec ntfy ntfy token add --label=phone phone
#    记下这一把，填进 App
```

### 为什么手机不能用后端那把令牌

ntfy 的访问令牌**授予该用户的完整账号权限**（官方文档原话：除改密码与删账号外，
用令牌可以做任何事）。后端那把是 `admin`，发给每台手机等于把实例管理权发出去了。
手机只需要"读某个 topic"，所以单独建 `phone` 用户 + `read-only` ACL。

> `oridesk-*` 要与你配置的 `ntfy_topic_prefix` 一致（默认 `oridesk`）。
> 改了前缀就要同步改 ACL，否则手机会订阅失败（表现为 `403`，App 日志里可见）。

## 4. 反向代理与 TLS

在 Nginx 里为 ntfy 加一个 server 块（后端主站配置见 `deploy/nginx/ticket.example.com.conf`）：

```nginx
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name ntfy.example.com;

    ssl_certificate     /etc/letsencrypt/live/ntfy.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ntfy.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:2586;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # ---- 长连接三件套：少一个都会出问题 ----
        # 1) 关缓冲：App 用 GET /<topic>/json 读 ndjson 流，
        #    Nginx 默认会把响应攒起来再发 —— 表现为"通知延迟几分钟才到"，
        #    而且看起来一切正常，极难定位。
        proxy_buffering off;
        proxy_request_buffering off;
        # 2) 读超时放宽：默认 60s 会把长连接反复切断，App 只能不停重连。
        proxy_read_timeout 1h;
        # 3) WebSocket 升级头（当前 App 用 /json，但留着不碍事，也方便用 ntfy 网页端）
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

申请证书与后端同法：

```bash
sudo certbot --nginx -d ntfy.example.com
sudo nginx -t && sudo systemctl reload nginx
```

验证：

```bash
curl -fsS https://ntfy.example.com/v1/health     # {"healthy":true}
```

## 5. 后端环境变量：**最容易踩的一个坑**

手机连的是**同一个后端域名**，所以后端域名必须在 `DJANGO_ALLOWED_HOSTS` 里 ——
否则所有手机请求会被 Django 以 **`400 DisallowedHost`** 拒掉，而 App 侧只表现为
"请求失败"，几乎无法自查。

```bash
# .env
DJANGO_ALLOWED_HOSTS=ticket.example.com,localhost,127.0.0.1
DJANGO_CSRF_TRUSTED_ORIGINS=https://ticket.example.com
```

> ⚠️ **具体陷阱**：如果你在 App 设置里填的是 `https://192.168.1.10`、
> `https://mail.internal` 这类**不在 `DJANGO_ALLOWED_HOSTS` 里**的地址，
> App 能打开网页（如果 Nginx 放行）但 API 一律 400。
> 要么把该地址加进 `DJANGO_ALLOWED_HOSTS`，要么统一用对外域名。

改完重建：

```bash
docker compose up -d web worker scheduler
curl -fsS https://ticket.example.com/healthz
```

## 6. 后端「系统设置 → 移动端推送」

用管理员账号登录后台 → **路由与系统设置 → 系统设置** → 页面下方的「移动端推送」区：

| 字段 | 填什么 | 注意 |
|---|---|---|
| 启用移动端推送 | ✅ | 默认关闭。关着时即使配了地址也不会发 |
| ntfy 服务地址 | `https://ntfy.example.com` | **必须手机能访问到**。填 `127.0.0.1` 或容器内网名 → 后端发得出去、手机订阅不到。填 `http://` 会被**拒绝**（客户端强制 HTTPS） |
| ntfy 访问令牌 | `--label=backend` 那把 `tk_…` | 以 Fernet 密文入库，页面永不回显。**留空 = 保持不变**（不会清空） |
| 清除已保存的 ntfy 令牌 | 一般不勾 | 只有确实要换/清令牌时才勾 |
| topic 前缀 | `oridesk` | 改了要同步改 ntfy 的 ACL |
| 通知聚合秒数 | `60` | 窗口内同一批事件合并为一条，避免一次收信刷屏 |
| 对外地址 | `https://ticket.example.com` | 推送里「在浏览器打开」的兜底链接。留空则通知只唤起 App |

## 7. 安装 App 与首次配置

APK 从 `ixiqiu/OriDesk-Android` 的 **Releases** 页面下载（打 tag 会自动发布），
或取 CI 产物。

1. 安装（首次需允许"安装未知来源应用"）。仓库**未配置签名密钥时**产出的是
   debug 签名包，**装新版前必须卸载**；配置了固定 keystore 之后可正常覆盖升级。
2. 打开 App → 顶部引导条 →「设置」
3. 服务器地址填 `https://ticket.example.com` → 保存（填 `http://` 会被明确拒绝）
4. 「打开登录页」→ 在应用内登录（复用网页会话）
5. 设备名称随便填（用于在后台辨认是哪台设备）
6. ntfy 访问令牌填 `--label=phone` 那把
7. 打开「启用推送」→ App 会调 `POST /api/mobile/subscriptions/` 注册本设备
8. 点「去设置电池白名单」，把 OriDesk 加入白名单

> **第 8 步不是可选项。** 国产 ROM 会杀后台，而方案 B 的推送依赖一个常驻长连接。
> 不加白名单，表现为"过一阵就收不到推送"。这是方案选择的已知代价，无法从代码根除。

## 8. 验证

按"从后往前"的顺序验，一次就能定位断在哪一段：

```bash
# ① 后端配置是否正确
docker compose exec web python -c "
import django, os; os.environ.setdefault('DJANGO_SETTINGS_MODULE','config.settings'); django.setup()
from apps.notifications import ntfy
print('enabled :', ntfy.is_enabled())
print('server  :', ntfy.server_url())
print('token   :', '已配置' if ntfy.get_token() else '未配置')
print('health  :', ntfy.health_check())
"
```

```bash
# ② ntfy 是否收到了后端的发布（订阅一个测试 topic，然后在 App 里点一次测试推送看 topic）
docker compose exec ntfy ntfy subscribe --poll oridesk-xxxx
```

**③ 最省事的一步**：App 设置页点「发送测试推送」。
它同步调用 `POST /api/mobile/subscriptions/<id>/test/`，**通没通立刻返回**——
这正是这个端点存在的意义：把"推送不通"和"App 有问题"两类故障分开。

通了之后，发一封测试邮件到系统邮箱，应当收到工单通知。

## 9. 故障排查

| 现象 | 最可能的原因 | 怎么办 |
|---|---|---|
| App 里所有请求都失败，但网页能开 | `DJANGO_ALLOWED_HOSTS` 没含手机填的地址 → `400` | 见 §5 |
| App 提示"登录状态已失效" | 会话过期，或 App 填的地址与登录用的不是同一个域 | 重新在 App 内登录一次 |
| 点启用推送提示"服务端未配置 ntfy 地址" | 系统设置里 `ntfy_server_url` 为空 | 见 §6 |
| 后端日志 `ntfy 发布失败：HTTP 401/403` | 后端令牌错，或 ACL 没放行 | 重发 `--label=backend` 的令牌；确认 `auth-default-access` |
| 后端显示发布成功，手机无反应 | **手机订阅用的是 http 地址**，或 App 里令牌错 | 确认 App 里 ntfy 令牌是 `phone` 那把；地址必须是 https |
| 通知延迟数分钟才到 | Nginx `proxy_buffering off` 没设 | 见 §4 |
| 过一阵就收不到推送 | ROM 杀后台 / 前台服务被限制 | 加电池白名单；确认通知权限；重开 App 会重新拉起服务 |
| 重启手机后不再推送 | 开机自启被系统拦（Android 12+ 限制后台启动前台服务） | 打开一次 App 即可恢复；部分 ROM 需手动允许自启动 |
| 手机上点通知没反应 | `mobile_public_base_url` 没配，且 scheme 唤起失败 | 配上对外地址作为兜底 |

查看 App 侧日志（需要 debug 包）：

```bash
adb logcat | grep -E "NtfyService|ApiClient|SecureStore"
```

## 10. 运维

### 备份

`ntfy_data` 卷里有**消息缓存**与**鉴权库**（`user.db`）：

- 缓存丢了只是丢历史，可重建；
- **`user.db` 丢了所有访问令牌失效**，需要重新签发并更新
  `ntfy_token` 设置项与每台手机的令牌。

建议把 `ntfy_data` 纳入备份范围（与 `db_data` 同级的策略）。

### 吊销一台设备

两种方式，效果不同：

- **只停本机接收**：App 设置里关掉「启用推送」。服务端记录仍在。
- **彻底吊销**：让用户在该设备上删除 App 数据，或在后台删除对应订阅记录。
  服务端 `Subscription` 删除后不再向该 topic 发布。

> ⚠️ 已经躺在 ntfy 缓存里的旧消息**无法撤回**（ntfy 没有删除 topic 的授权模型）。
> 缓解办法是吊销后重新注册 —— 新 topic 是新频道。

### 轮换令牌

```bash
docker compose exec ntfy ntfy token add --label=backend-new oridesk   # 先发新的
# 更新系统设置里的 ntfy 令牌
docker compose exec ntfy ntfy token remove oridesk tk_旧令牌
```

手机令牌同理，逐台更新。

### 容量

ntfy 很轻（Go 单二进制 + SQLite）。默认消息缓存 12h，附件功能我们**不用**
（推送里只有工单号与主题，不放邮件正文），所以 `ntfy_data` 增长有限。
若长期运行后缓存文件偏大，可在 compose 里调 `NTFY_CACHE_DURATION`
（默认 `12h`，调小会缩短断线补齐的时间窗）。

## 11. 隐私边界（别越线）

推送内容**只含工单号与主题，绝不含邮件正文**。这是刻意的设计约束：

- 推送要经过 ntfy（即使是自建），邮件正文是客户隐私；
- 用户点击通知后回 App 看全文，正文不过第二台服务器。

改动通知文案时**不要**把 `Message.body_text` 放进推送载荷。
相关约束记在 `docs/移动端API约定.md` §4.3 与 `tests/test_notifications_services.py`
的 `test_title_and_body_carry_no_email_body` 用例里。
