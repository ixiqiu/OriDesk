# 部署手册 · 新技元邮箱及工单管理系统（OriDesk）

适用版本：Django 5.2 + MariaDB 11 + Redis 7 + RQ + APScheduler，Docker Compose 部署，宿主 Nginx 反向代理。
配套文件：`Dockerfile`、`docker-compose.yml`、`docker/entrypoint.sh`、`deploy/nginx/ticket.example.com.conf`、`scripts/backup.sh`、`scripts/restore.sh`。

本文所有命令中的 `/data/dsh/home/OriDesk` 为项目目录、`ticket.example.com` 为示例域名，请按实际环境替换。

## 2. 首次部署步骤

### 步骤 1：准备宿主目录与权限

容器内所有 Python 进程以 **uid/gid 10001** 运行（`Dockerfile` 中的 `app` 用户），绑定挂载目录必须提前授权，否则 `collectstatic` 与附件落盘会失败。

```bash
sudo mkdir -p /srv/ticket-system/{media,staticfiles,backups}
sudo chown -R 10001:10001 /srv/ticket-system/media /srv/ticket-system/staticfiles
sudo chmod 700 /srv/ticket-system/backups
# Nginx（www-data）需要能读到静态与媒体目录
sudo chmod o+rx /srv/ticket-system /srv/ticket-system/staticfiles /srv/ticket-system/media
stat -c '%a %u:%g %n' /srv/ticket-system /srv/ticket-system/*
```

### 步骤 2：获取代码

```bash
sudo mkdir -p /opt && cd /opt
sudo git clone <代码仓库地址> OriDesk     # 或解压发布包
cd /opt/OriDesk
ls Dockerfile docker-compose.yml docker/entrypoint.sh scripts/backup.sh
```

> 本文其余命令统一在项目目录下执行；如部署路径不是 `/opt/OriDesk`，请同步修改 Nginx 配置注释里的路径引用与 cron 中的路径。

### 步骤 3：生成生产 `.env`

```bash
cp .env.example .env
chmod 600 .env

# 三个密钥一律现场生成，绝不沿用 .env.example 里的示例文本
sed -i "s|^DJANGO_SECRET_KEY=.*|DJANGO_SECRET_KEY=$(openssl rand -base64 48)|" .env
sed -i "s|^DB_PASSWORD=.*|DB_PASSWORD=$(openssl rand -base64 24 | tr -d '/+=')|" .env
sed -i "s|^DB_ROOT_PASSWORD=.*|DB_ROOT_PASSWORD=$(openssl rand -base64 24 | tr -d '/+=')|" .env
sed -i "s|^FERNET_KEY=.*|FERNET_KEY=$(openssl rand -base64 32 | tr '+/' '-_')|" .env

# 填入域名（务必与证书、CSRF_TRUSTED_ORIGINS 一致）
sed -i "s|^DJANGO_ALLOWED_HOSTS=.*|DJANGO_ALLOWED_HOSTS=ticket.example.com|" .env
sed -i "s|^DJANGO_CSRF_TRUSTED_ORIGINS=.*|DJANGO_CSRF_TRUSTED_ORIGINS=https://ticket.example.com|" .env

# 首次上线建议先把 HSTS 调小，稳定后再放大（见 FAQ Q13）
grep -q '^DJANGO_SECURE_HSTS_SECONDS=' .env || echo 'DJANGO_SECURE_HSTS_SECONDS=300' >> .env

# 逐项核对（不要跳过）
grep -vE '^\s*#|^\s*$' .env
```

`.env` 关键值应满足：

| 变量 | 期望值 |
|---|---|
| `DB_ENGINE` | `mysql` |
| `DB_NAME` / `DB_USER` | `ticket_system` / `ticket`（与 compose 中 `MARIADB_*` 一致） |
| `DB_HOST` / `DB_PORT` | `db` / `3306` |
| `DJANGO_DEBUG` | `False` |
| `REDIS_URL` | `redis://redis:6379/0` |
| `IMAP_POLL_INTERVAL_SECONDS` | `60`（可按需调大，如 `120`） |

**立即把 `FERNET_KEY` 抄送进密码管理器**：它决定邮箱授权码能否解密，数据库备份里存的只是密文。

```bash
grep '^FERNET_KEY=' .env    # 复制该值到密码管理器，切勿粘贴到聊天工具/工单系统
```

### 步骤 4：部署前代码自检

`check` / `migrate` / `collectstatic` 都会先跑 Django 系统检查，其中包含 URLConf 导入。就绪门槛与 CI（`.github/workflows/ci.yml`）一致：

```bash
# 1) 构建镜像并做配置自检（--no-deps 不启动 db/redis，check 不需要连库）
docker compose run --rm --no-deps --entrypoint python web manage.py check
#    期望：System check identified no issues (0 silenced).

# 2) 确认没有"模型改了但迁移没生成"
docker compose run --rm --no-deps --entrypoint python web manage.py makemigrations --check --dry-run
#    期望：No changes detected（本项目禁止手写迁移，有变更必须由开发补迁移）

# 3) 生产安全配置自检（关注 DEBUG / SECRET_KEY / HSTS / Cookie 相关告警）
docker compose run --rm --no-deps --entrypoint python web manage.py check --deploy
#    以上任一步失败即视为"未就绪"，先修复再进入步骤 5。
```

测试请在**开发机或 CI** 上跑（生产镜像只安装 `requirements.txt`，不含 pytest）：

```bash
python -m pytest -q                 # SQLite 单测
python -m pytest -q --cov=apps      # 覆盖率
```

若确需在容器内跑测试，先装开发依赖再执行：

```bash
docker compose run --rm --no-deps --entrypoint sh web -c 'pip install -r requirements-dev.txt && python -m pytest -q'
```

## 3. 环境变量逐项说明

`config/settings.py` 通过项目根目录的 `.env` 加载环境变量（已存在的真实环境变量优先）。容器内 `docker-compose.yml` 会额外强制覆盖连接拓扑类变量。

### 3.1 Django 基础

| 变量 | 必填 | 示例 | 说明 |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | 是 | `$(openssl rand -base64 48)` | 会话签名、CSRF 等用途。非 DEBUG 环境下缺失会直接 `ImproperlyConfigured` 拒绝启动 |
| `DJANGO_DEBUG` | 是 | `False` | **生产必须 False**。True 会关闭全部安全开关并暴露调试页 |
| `DJANGO_ALLOWED_HOSTS` | 是 | `ticket.example.com` | 逗号分隔；禁止 `*`。测试环境会自动追加 `testserver` |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | 是 | `https://ticket.example.com` | 逗号分隔，必须带协议前缀；缺失会导致后台表单 403 |
| `DJANGO_TIME_ZONE` | 否 | `Asia/Shanghai` | 默认 `Asia/Shanghai`；数据库统一存 UTC（`USE_TZ=True`） |
| `DJANGO_SECURE_SSL_REDIRECT` | 否 | `True` | 仅在 `DEBUG=False` 时生效；本地无 HTTPS 时置 `False` |
| `DJANGO_SECURE_HSTS_SECONDS` | 否 | `31536000` | 默认一年。首次上线建议 `300`，稳定后放大 |
| `DJANGO_SECURE_HSTS_PRELOAD` | 否 | `False` | 保持 `False`，除非确定要提交 HSTS 预加载列表 |
| `SKIP_ENV_CHECK` | 否 | `0` | 容器入口的示例值检查开关；**生产禁止设 1** |

### 3.2 数据库

| 变量 | 必填 | 示例 | 说明 |
|---|---|---|---|
| `DB_ENGINE` | 是 | `mysql` | `mysql`/`mariadb` 走 MariaDB；`sqlite` 走本地文件。生产用 `mysql` |
| `DB_NAME` | 是 | `ticket_system` | 必须与 compose 的 `MARIADB_DATABASE` 一致 |
| `DB_USER` | 是 | `ticket` | 必须与 `MARIADB_USER` 一致；该账号对自身库拥有全部权限，够用（恢复也不需要 root） |
| `DB_PASSWORD` | 是 | `CHANGE_ME` | 仅字母数字，避免 shell/连接串转义问题；compose 用 `${DB_PASSWORD:?}` 强制校验 |
| `DB_HOST` | 是 | `db` | 容器内由 compose 强制为 `db`，防止误连 SQLite 空库 |
| `DB_PORT` | 是 | `3306` | 容器内由 compose 强制 |
| `DB_ROOT_PASSWORD` | 是 | `CHANGE_ME` | 供 compose 的 `MARIADB_ROOT_PASSWORD`、恢复脚本的建库兜底、以及运维查询（`information_schema`/全局状态）使用；应用连接不用 root |
| `DB_WAIT_TIMEOUT` | 否 | `60` | 容器入口等待数据库就绪的最长秒数 |

### 3.3 凭据加密与队列

| 变量 | 必填 | 示例 | 说明 |
|---|---|---|---|
| `FERNET_KEY` | 是 | `$(openssl rand -base64 32 \| tr '+/' '-_')` | urlsafe base64 的 32 字节密钥。邮箱授权码用它加密；**丢失或更换后所有邮箱凭据需重录**，必须单独备份 |
| `REDIS_URL` | 是 | `redis://redis:6379/0` | RQ broker；容器内由 compose 强制为 `redis://redis:6379/0` |
| `REDIS_WAIT_TIMEOUT` | 否 | `60` | 容器入口等待 Redis 就绪的最长秒数 |
| `IMAP_POLL_INTERVAL_SECONDS` | 否 | `60` | IMAP 轮询间隔；数据库 `settings.imap_poll_interval_seconds` 可覆盖，环境变量优先。实现层下限为 10 秒 |

### 3.4 存储与编排

| 变量 | 必填 | 示例 | 说明 |
|---|---|---|---|
| `HOST_MEDIA_DIR` | 否 | `/srv/ticket-system/media` | compose 绑定挂载到容器 `/app/media`（默认值即此） |
| `HOST_STATIC_DIR` | 否 | `/srv/ticket-system/staticfiles` | 绑定挂载到容器 `/app/staticfiles`（默认值即此） |
| `WEB_PORT` | 否 | `8000` | 宿主 `127.0.0.1:<port>` → 容器 8000；改这里要同步改 Nginx `upstream` |
| `APP_ROLE` | compose 注入 | `web` / `worker` / `scheduler` | 决定是否执行 `migrate` 与 `collectstatic`；手工 `docker run` 时默认 `web` |
| `MEDIA_ROOT` | 否 | `/app/media` | 与 `settings.py` 一致；一般无需设置 |
| `ATTACHMENT_X_ACCEL_PREFIX` | **是**（生产） | `/media/attachments/` | 附件下发前缀：设置后由 Nginx `internal` location 传输（推荐）；留空则由 Django 自己流式返回。必须与 Nginx 配置成对，见 §4.2 |

### 3.5 备份与恢复

| 变量 | 必填 | 示例 | 说明 |
|---|---|---|---|
| `BACKUP_DIR` | 否 | `/srv/ticket-system/backups` | 备份输出目录，脚本会 `mkdir -p` 并 `chmod 700` |
| `BACKUP_RETENTION_DAYS` | 否 | `14` | 按 mtime 清理 `ticket-*`，必须为正整数 |
| `BACKUP_INCLUDE_ENV` | 否 | `0` | 设为 `1` 会把 `.env`（含密钥）一并复制进备份目录，仅在你已对备份目录加密时开启 |
| `COMPOSE_FILE` | 否 | `<项目>/docker-compose.yml` | 备份/恢复脚本调用的 compose 文件 |
| `BACKUP_DB_HOST` / `BACKUP_DB_PORT` | 否 | `127.0.0.1` / `3306` | 仅"非容器化 + 宿主客户端"备份路径使用 |
| `SKIP_SAFETY_BACKUP` | 否 | `0` | 恢复脚本设为 `1` 可跳过"恢复前现状快照"（不推荐） |

## 4. Nginx 配置说明

文件：`deploy/nginx/ticket.example.com.conf`。安装步骤：

```bash
sudo cp deploy/nginx/ticket.example.com.conf /etc/nginx/sites-available/ticket.example.com.conf
sudo sed -i 's/ticket\.example\.com/你的域名/g' /etc/nginx/sites-available/ticket.example.com.conf
sudo ln -sf /etc/nginx/sites-available/ticket.example.com.conf /etc/nginx/sites-enabled/ticket.example.com.conf
sudo nginx -t && sudo systemctl reload nginx
```

### 4.1 各段作用

| 配置段 | 作用 | 修改时注意 |
|---|---|---|
| `upstream oridesk_app` | 指向 `127.0.0.1:8000`，`keepalive 16` | 改 `WEB_PORT` 时必须同步改这里 |
| 80 端口 server | 全量 301 到 HTTPS，但放行 `/.well-known/acme-challenge/` | ACME 放行必须在跳转之前，否则证书无法自动续期 |
| `ssl_certificate*` / `ssl_protocols` | 证书与 TLS 1.2/1.3 | 路径由 certbot 管理，勿手工编辑 |
| `client_max_body_size 30M` | 上传上限，比应用侧 `max_attachment_size_mb=25` 留余量 | 调大应用上限时同步调大，否则先收到 413 |
| `location ^~ /static/` | 直出 `collectstatic` 产物，`expires 30d` | `alias` 必须指向宿主 `HOST_STATIC_DIR`；单独补 `nosniff`（不经 Django） |
| `location ^~ /media/attachments/` | 附件**内部**重定向（`internal`）：只接受来自 Django 的 `X-Accel-Redirect` | 见 §4.2；必须与 `.env` 的 `ATTACHMENT_X_ACCEL_PREFIX` 成对配置 |
| `location ^~ /media/` | 直出其余媒体（富文本内嵌图片等） | 不要在其中存放敏感文件 |
| `location = /healthz` | 反代健康检查，`access_log off` | 探测频率高，关日志避免刷屏；`proxy_read_timeout 10s` |
| `location /` | 应用主入口，全套转发头 | 见 §4.3 |
| `location ~ /\.(?!well-known)` | 拒绝探测 `.env` / `.git` 等隐藏路径 | 与 ACME 放行不冲突 |
| `gzip *` | 文本类响应压缩 | 只压文本；图片/压缩包本身已压缩 |

### 4.2 附件出站路径（已默认安全，配置必须成对）

附件**不再由 Nginx 直出**，而是"应用层鉴权 + 内部重定向"：

1. 浏览器访问 `/attachments/<id>/download/`（或 `/preview/`）；
2. `apps/tickets/views.py::_serve_attachment` 校验登录 + 工单可见性，危险扩展名（`.exe` 等）拒绝预览；
3. 通过后返回 `X-Accel-Redirect: /media/attachments/attachments/<ticket_id>/<message_key>/<filename>`；
4. Nginx 的 `location ^~ /media/attachments/` 为 `internal`，**只**响应上述内部重定向，匿名直链一律 404。

**必须成对配置**（否则附件 404 或退化为直出）：

```env
# .env
ATTACHMENT_X_ACCEL_PREFIX=/media/attachments/
```

```nginx
# deploy/nginx/ticket.example.com.conf
location ^~ /media/attachments/ {
    internal;
    alias /srv/ticket-system/media/;   # 注意：指向媒体根目录（URI 里已含一层 attachments/）
    ...
}
```

路径映射不变量：

```text
X-Accel-Redirect = ATTACHMENT_X_ACCEL_PREFIX + <数据库 attachments.path>
attachments.path = attachments/{ticket_id}/{message_key}/{filename}
URI              = /media/attachments/attachments/12/msg-abc/报告.pdf
磁盘文件          = /srv/ticket-system/media/attachments/12/msg-abc/报告.pdf
```

若把 `ATTACHMENT_X_ACCEL_PREFIX` 留空，Django 会自己流式返回附件（单机/本地开发可用，
但大文件会占用 web 进程带宽）。**不要把该 location 改回直出**：那会让附件绕过工单可见性
（路径中的 `ticket_id` 是自增整数，枚举成本极低）。

其余 `/media/`（富文本内嵌图片等）仍为直出，请勿在其中存放敏感文件。

### 4.3 转发头与超时

| 头 | 为什么必须有 |
|---|---|
| `X-Forwarded-Proto $scheme` | `settings.py` 的 `SECURE_PROXY_SSL_HEADER=("HTTP_X_FORWARDED_PROTO","https")` 依赖它；缺失会让 Django 认为请求是 http 而触发无限 301 |
| `Host` / `X-Forwarded-Host` | `USE_X_FORWARDED_HOST=True`，且 `ALLOWED_HOSTS` 按域名校验；缺失会 400 |
| `X-Real-IP` / `X-Forwarded-For` | 审计日志与登录风控需要真实客户端 IP |
| `X-Forwarded-Port` / `X-Forwarded-Server` | 便于排障与后续扩展 |
| `Connection ""` | 配合 `upstream keepalive` 复用后端长连接 |

超时：Gunicorn 使用 compose 中固定的启动命令 `gunicorn config.wsgi:application -b 0.0.0.0:8000`，**Gunicorn 默认 `--timeout 30s`**，Nginx 侧设为 `proxy_read_timeout 65s` / `proxy_send_timeout 65s`，始终比后端大，避免 Nginx 先返回 504 掩盖真实错误。若日后给 Gunicorn 增加 `--timeout 120`，Nginx 同步改为 `125s`。

### 4.4 安全响应头

HSTS、`X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options` 由 Django `SecurityMiddleware` 输出（`settings.py` 在 `DEBUG=False` 时开启）。Nginx 只在**不经过 Django** 的 `/static/`、`/media/` 内补齐 `X-Content-Type-Options`，避免同名重复响应头。

## 5. TLS 证书（certbot）

HTTPS server 块引用了 `/etc/letsencrypt/live/<域名>/` 下的证书，**证书不存在时 `nginx -t` 会失败**，所以首次签发必须走在安装正式配置之前。

### 5.1 首次签发（webroot，推荐）

```bash
sudo mkdir -p /var/www/certbot

# 1) 临时最小站点，仅用于通过 http-01 校验
sudo tee /etc/nginx/sites-available/oridesk-acme.conf >/dev/null <<'EOF'
server {
    listen 80;
    server_name ticket.example.com;
    location ^~ /.well-known/acme-challenge/ { root /var/www/certbot; }
    location / { return 404; }
}
EOF
sudo ln -sf /etc/nginx/sites-available/oridesk-acme.conf /etc/nginx/sites-enabled/oridesk-acme.conf
sudo nginx -t && sudo systemctl reload nginx

# 2) 签发
sudo certbot certonly --webroot -w /var/www/certbot -d ticket.example.com \
  --agree-tos -m admin@example.com --no-eff-email
sudo ls -l /etc/letsencrypt/live/ticket.example.com/

# 3) 撤掉临时站点，换成正式配置（正式配置的 80 块同样放行 ACME）
sudo rm -f /etc/nginx/sites-enabled/oridesk-acme.conf
sudo cp /opt/OriDesk/deploy/nginx/ticket.example.com.conf /etc/nginx/sites-available/ticket.example.com.conf
sudo sed -i 's/ticket\.example\.com/你的域名/g' /etc/nginx/sites-available/ticket.example.com.conf
sudo ln -sf /etc/nginx/sites-available/ticket.example.com.conf /etc/nginx/sites-enabled/ticket.example.com.conf
sudo nginx -t && sudo systemctl reload nginx
```

备选：`sudo certbot certonly --standalone -d ticket.example.com`（需临时停掉 Nginx 以释放 80 端口）。

### 5.2 自动续期

```bash
# webroot 方式不会自动 reload nginx，加一个部署钩子
sudo mkdir -p /etc/letsencrypt/renewal-hooks/deploy
sudo tee /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh >/dev/null <<'EOF'
#!/bin/sh
systemctl reload nginx
EOF
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh

# 验证续期链路（不会真的签发）
sudo certbot renew --dry-run
systemctl list-timers | grep -i certbot     # 确认存在自动续期定时器
```

### 5.3 证书相关注意点

| 事项 | 说明 |
|---|---|
| 到期告警 | 除 `certbot renew` 外，建议加外部探针检查证书剩余天数（< 14 天告警） |
| HSTS 与证书 | HSTS 生效期间证书故障会导致站点完全打不开且无法绕过，首次上线先小值（§3.1） |
| 多域名 | 需要多个域名时在 certbot 命令里追加 `-d`，并在 Nginx 配置的 `server_name` 中同步 |
| 泛域名 | 泛域名只能 DNS-01 校验，需要 DNS 服务商插件，与本配置无关 |
| 私钥权限 | `privkey.pem` 仅 root 可读；Nginx master 以 root 启动，属正常 |

### 6.1 升级前

```bash
cd /opt/OriDesk
git rev-parse --short HEAD                      # 记录当前版本（发布包部署则记录包版本号）

sudo ./scripts/restore.sh --list               # 确认备份集已生成、校验清单齐全
```

### 6.2 升级步骤（建议放在维护窗口）

```bash
cd /opt/OriDesk
git fetch --all --tags && git checkout <新版本 tag>
docker compose build
docker compose up -d                            # 滚动重建；web 入口自动执行 migrate
docker compose logs -f --tail=200 web           # 观察 migrate 输出
```

升级后抽查清单：

| 检查项 | 命令 | 期望 |
|---|---|---|
| 迁移已应用 | `docker compose exec web python manage.py showmigrations \| grep '\[ \]'` | 无输出（没有未应用迁移） |
| 静态资源 | `curl -sI https://<域名>/static/admin/css/base.css` | 200 |
| 健康检查 | `curl -fsS https://<域名>/healthz` | `{"status":"ok","database":true}` |

| 收信正常 | `docker compose logs --tail=50 scheduler` | 有新的 `IMAP 轮询开始` 与处理日志 |
| 发信正常 | 在界面上回复一封测试工单 | 审计日志有 `reply` 记录，客户收到邮件 |

### 6.3 回滚

Django 迁移**不保证可逆**（`migrate` 没有自动回滚；`migrate <app> <前一个迁移>` 只在迁移写了 `RunPython` 反向操作时可用）。因此回滚的正解是"回滚代码 + 恢复升级前的数据库备份"。

```bash
cd /opt/OriDesk

# 1) 停应用，保留 db/redis
docker compose stop web worker scheduler

# 2) 回滚代码（或镜像 tag）
git checkout <升级前版本 tag>
docker compose build

# 3) 若新版本执行过破坏性迁移：恢复升级前的备份
#    先看有哪些备份（升级前那次的时间戳）
sudo ./scripts/restore.sh --list
sudo ./scripts/restore.sh --stamp <升级前的时间戳> --yes

# 4) 启动并验证
docker compose up -d
curl -fsS http://127.0.0.1:8000/healthz ; echo
```

**恢复旧数据后必须执行 IMAP 位点核对**（否则会把备份点之后的邮件重新拉成工单），步骤见 §7.4。

### 6.4 维护窗口与影响

| 操作 | 影响 |
|---|---|
| `docker compose up -d`（仅重建 web） | 数秒 502，客户端刷新即可 |
| 停 `worker` | 已入队任务暂停处理；发信延迟，不丢任务（Redis AOF 开启） |
| 停 `scheduler` | IMAP 暂停拉取；邮件仍在服务端，恢复后按 `last_uid` 补拉，不丢信 |
| 停 `db` | 全站不可用，必须避免 |
| 恢复备份 | 全站停写；恢复期间客户的来信在服务端排队，恢复后补拉 |

## 7. 备份与恢复演练

### 7.1 备份策略

| 对象 | 方式 | 频率 | 保留 | 位置 |
|---|---|---|---|---|
| MariaDB | `mariadb-dump --single-transaction --hex-blob --default-character-set=utf8mb4` | 每日 02:30 | 14 天（`BACKUP_RETENTION_DAYS`） | `/srv/ticket-system/backups` |
| 附件 media | `tar -czf`（归档根目录 `media/`） | 每日 02:30 | 同上 | 同上 |
| 校验清单 | `sha256sum` → `ticket-<时间戳>.sha256` | 每次备份 | 同上 | 同上 |
| `FERNET_KEY` | **人工**存入密码管理器 | 变更时 | 永久 | 密码管理器 / 独立保管 |
| `.env` | 默认不备份；`BACKUP_INCLUDE_ENV=1` 可选 | — | — | 同上 |

产物命名：`ticket-db-<UTC时间戳>.sql.gz`、`ticket-media-<UTC时间戳>.tar.gz`、`ticket-<UTC时间戳>.sha256`（恢复前的现状快照带 `-pre-restore` 后缀）。

**备份目录权限为 700、文件为 600**：备份内含客户邮件正文、附件等个人信息，请纳入加密与异地存放流程。备份期间避免执行数据库迁移（DDL 会被单事务快照排除，导致结构与数据版本不一致）。

### 7.2 备份与校验命令

```bash
sudo /opt/OriDesk/scripts/backup.sh
sudo /opt/OriDesk/scripts/restore.sh --list
# 手工校验最新一套备份的完整性
cd /srv/ticket-system/backups && sudo sha256sum -c "$(ls -1t ticket-*.sha256 | head -1)"
# 备份是否断档（最新备份距今超过 26 小时应告警）
sudo find /srv/ticket-system/backups -name 'ticket-db-*.sql.gz' -mmin -1560 | wc -l
```

### 7.3 恢复流程（`scripts/restore.sh` 已实现的安全动作）

1. 校验 `ticket-<时间戳>.sha256`，不通过直接退出（不会用损坏备份覆盖生产）。
2. 打印影响范围并要求输入 `yes` 确认（自动化用 `--yes`）。
3. 恢复前自动做一次现状快照（`BACKUP_TAG=pre-restore`），失败则中止。
4. `docker compose stop web worker scheduler`，避免恢复期间仍在收信/发信。
5. 数据库：`CREATE DATABASE IF NOT EXISTS ... utf8mb4/utf8mb4_unicode_ci` → 关闭外键/唯一键检查导入 → 校验表数量。
6. media：解压到暂存目录 → 原目录改名保留为 `<media>.before-restore-<时间戳>` → 原子替换 → `chown 10001:10001`。
7. `docker compose up -d web worker scheduler` → 轮询 `/healthz`（最长 150 秒）。
8. 打印"恢复后必做"清单（见 §7.4）。

### 7.4 恢复后必做：IMAP 位点核对（防重复工单）

备份是**时间点快照**，`mailboxes.last_uid` / `uidvalidity` 会一并回退。若恢复后立刻放开调度器，IMAP 会从备份点的 UID 重新拉取：

- 已在库中的邮件有幂等保护（`apps/mailboxes/pipeline.py::already_seen` 按 `(mailbox, Message-ID, direction=in)` 去重），不会重复入库；
- **备份点之后收到的新邮件会被重新处理**，可能重新建单、重新发自动回复。

因此恢复后按下面顺序操作：

```bash
cd /opt/OriDesk
docker compose exec db sh -c 'MYSQL_PWD="$MARIADB_PASSWORD" mariadb \
  -u"$MARIADB_USER" "$MARIADB_DATABASE" -e "UPDATE mailboxes SET is_active = 0"'

docker compose exec db sh -c 'MYSQL_PWD="$MARIADB_PASSWORD" mariadb \
  -u"$MARIADB_USER" "$MARIADB_DATABASE" \
  -e "SELECT id, email, last_uid, uidvalidity, is_active FROM mailboxes ORDER BY id"'
```

对每个邮箱核对：

| 情况 | 处置 |
|---|---|
| 备份时间离现在很近（分钟级），`last_uid` 与服务端基本一致 | 直接置回 `is_active = 1`，观察一轮同步日志 |
| 备份明显早于现在 | 先算出该邮箱服务端当前的 `UIDNEXT`，把 `last_uid` 置为 `UIDNEXT - 1`、`uidvalidity` 置为当前值，再 `is_active = 1` |
| 无法确认服务端 UID | 保持 `is_active = 0`，逐个邮箱启用并盯着 `docker compose logs -f scheduler`，一旦出现重复建单立即冻结并清理 |

`uidvalidity` 与 `last_uid` 可直接改库（这两列不参与业务校验，仅用于增量同步）：

```bash
docker compose exec db sh -c 'MYSQL_PWD="$MARIADB_PASSWORD" mariadb \
  -u"$MARIADB_USER" "$MARIADB_DATABASE" \
  -e "UPDATE mailboxes SET last_uid = 12345, uidvalidity = 67890, is_active = 1 WHERE email = \"support@example.com\""'
```

> 说明：外层用单引号包裹 `sh -c`，所以 SQL 里的字符串用双引号表示。当前 sql_mode 未启用 `ANSI_QUOTES`，双引号与单引号等价；若日后开启 `ANSI_QUOTES`，请把字符串改写成 `'\''support@example.com'\''` 形式的单引号转义。

## 8. 监控与日志

### 8.1 监控项与阈值

| 监控项 | 检查方式 | 告警阈值 | 处置 |
|---|---|---|---|
| Web 存活 | 外部探针 `curl -fsS https://<域名>/healthz`（1 分钟） | 连续 3 次非 200 | 重启 `web`；若 503 说明数据库不可达 |
| 容器健康 | `docker compose ps --format '{{.Service}} {{.Status}}'` | 任一非 `healthy` | 见 §9 对应行 |
| 队列积压 | `docker compose exec redis redis-cli LLEN rq:queue:mail` | `> 100` 且持续 5 分钟 | 检查 worker 是否存活、是否有超长任务 |
| 失败任务 | `docker compose exec redis redis-cli ZCARD rq:failed:mail` | `> 0` | 查看容器日志定位异常任务 |
| Worker 心跳 | `docker compose exec redis redis-cli --scan --pattern 'rq:worker:*'` 后逐个 `TTL` | 无键或 TTL 为负 | `docker compose restart worker` |
| IMAP 同步 | 每个邮箱最近入站邮件时间（SQL 见运维手册 §2） | 超过轮询间隔 ×3 | 检查授权码、UIDVALIDITY、scheduler 日志 |
| 出站邮件量 | 按小时聚合 `messages` 中 `direction='out'` | 突增或自动回复占比 > 80% | 按邮件风暴预案处置（运维手册 §3.3） |
| 磁盘使用率 | `df -h /srv` + `du -sh /srv/ticket-system/*` | `> 80%` | 清理旧备份、归档附件、扩容 |
| MariaDB 体积 | `information_schema` 汇总（见运维手册 §2） | 环比增长异常 | 检查是否被退信/批量邮件灌入 |
| 备份是否断档 | 最新 `ticket-db-*.sql.gz` 的 mtime | 超过 26 小时 | 检查 cron 与 `/var/log/oridesk-backup.log` |
| TLS 证书 | `openssl s_client -connect <域名>:443 -servername <域名> </dev/null 2>/dev/null \| openssl x509 -noout -enddate` | 剩余 < 14 天 | `sudo certbot renew`，检查续期定时器 |

外部探针示例（cron，每分钟）：

```cron
* * * * * curl -fsS --max-time 10 https://ticket.example.com/healthz >/dev/null || logger -t oridesk "healthz FAILED"
```

### 8.2 日志位置与轮转

| 日志 | 位置 / 查看方式 | 轮转 |
|---|---|---|
| 应用（web/worker/scheduler） | `docker compose logs -f --tail=200 <服务>` | compose 已配 `json-file`，单文件 10 MB × 5 |
| Nginx 访问日志 | `/var/log/nginx/ticket.example.com.access.log` | 由系统 logrotate（Debian/Ubuntu 自带 nginx 规则） |
| Nginx 错误日志 | `/var/log/nginx/ticket.example.com.error.log` | 同上 |
| 备份日志 | `/var/log/oridesk-backup.log`（cron 重定向） | 建议加入 `/etc/logrotate.d/oridesk` |
| MariaDB | `docker compose logs db` | compose 已配 10 MB × 5 |
| 审计日志（业务层） | 数据库 `audit_logs` 表 + 管理后台 `/audit/` | 随备份保留 |

```bash
# 备份日志轮转
sudo tee /etc/logrotate.d/oridesk >/dev/null <<'EOF'

    weekly
    rotate 8
    compress
    missingok
    notifempty
    create 0600 root root

```

### 8.3 关键日志关键字

| 关键字 | 出处 | 含义与处置 |
|---|---|---|
| `IMAP 轮询开始：` | `runapscheduler` | 调度器心跳正常 |
| `UIDVALIDITY 变化（… → …），重置同步位点。` | `apps/mailboxes/sync.py` | 服务端邮箱被重建，`last_uid` 已归零，可能出现补拉；见运维手册 §3.2 |
| `命中防循环规则（…），已丢弃。` | `apps/mailboxes/pipeline.py` | 防循环生效；频繁出现说明有回环或批量邮件涌入 |
| `处理失败，将在下一轮重试。` | `apps/mailboxes/sync.py` | 单封邮件处理异常，位点未推进，会重试 |
| `自动回复发送失败` | `apps/mailboxes/pipeline.py` | SMTP 异常；查授权码与网络 |

## 附录 B：MariaDB 注意事项

### B.1 字符集与排序规则

- 服务器：`--character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci`（compose 已固定）。
- 连接：`settings.py` 的 `OPTIONS.charset = "utf8mb4"`。
- 库：恢复脚本用 `CREATE DATABASE ... CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` 兜底。
- 巡检：
  ```sql
  SELECT DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
  FROM information_schema.SCHEMATA WHERE SCHEMA_NAME = 'ticket_system';

  SELECT table_name, table_collation FROM information_schema.tables
  WHERE table_schema = 'ticket_system' AND table_collation NOT LIKE 'utf8mb4%';
  ```
  第二条应返回空集；若有行，说明该表不是 utf8mb4，中文排序与 emoji 存储都会出问题。

### B.2 严格模式

连接级由 `init_command` 设置 `sql_mode='STRICT_TRANS_TABLES'`；服务器默认 sql_mode 也被 compose 设为 `STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION`。这样超长字符串、非法日期会直接报错而不是被静默截断。

```sql
SELECT @@sql_mode;   -- 会话级，应包含 STRICT_TRANS_TABLES
SHOW VARIABLES LIKE 'sql_mode';   -- 服务器默认
```

### B.3 带 `condition` 的 `UniqueConstraint` 会被静默跳过（重要）

- 事实：Django 5.2 在 MySQL/MariaDB 上 `supports_partial_indexes = False`，`django/db/backends/base/schema.py::_unique_supported()` 因此返回 `False`，`UniqueConstraint(condition=...)` **不会生成任何索引，也不会报错**。
- 影响：`Mailbox.Meta.constraints` 里的 `unique_fallback_mailbox`（`fields=["is_fallback"], condition=Q(is_fallback=True)`）在 MariaDB 上完全没有数据库层保护。
- 保证方式：应用层 `apps/accounts/models.py::Mailbox._assert_fallback_unique()`（由 `save()` / `clean()` 调用）。
- 巡检（期望 ≤ 1 行）：
  ```sql
  SELECT id, email, is_fallback, is_active FROM mailboxes WHERE is_fallback = 1;
  SELECT index_name, column_name, non_unique FROM information_schema.STATISTICS
  WHERE table_schema = 'ticket_system' AND table_name = 'mailboxes';
  ```
  第二条里**不会**出现针对 `is_fallback` 的唯一索引，这是预期现象，不要误判为"索引建漏了"而手工补建部分索引（MariaDB 不支持，会失败）。
- 发现多行 `is_fallback = 1`（例如直接改库或并发写入绕过 `save()`）时，人工保留一个、其余置 `0`，并检查 `settings.fallback_mailbox_id` 是否指向被保留的那一个。

### B.4 500 字符索引字段的开销

`tickets.normalized_subject`、`messages.message_id` 为 `CharField(max_length=500)` 且建索引：

- utf8mb4 下单字符最多 4 字节 → 索引键最长 2000 字节；
- MariaDB 11 默认 `DYNAMIC` 行格式 + `innodb_large_prefix`（默认开），索引键上限 3072 字节，因此**能建成功**；
- 代价：二级索引里要存完整的 2000 字节键，索引体积与写入放大明显，`EXPLAIN` 里也要留意这类索引的选择性（`normalized_subject` 通常选择性低，价值有限）；
- 若行格式为 `COMPACT` 或关闭大前缀，会直接报 `ERROR 1071 Specified key was too long; max key length is 767 bytes`；
- 需要索引的长字段建议控制在 191 字符以内或使用前缀索引；调整字段长度属于模型变更，需人工确认（开发文档 §10.4 禁止 AI 自行改 Model 字段）。

巡检：

```sql
SELECT table_name, index_name, column_name, sub_part, cardinality
FROM information_schema.STATISTICS
WHERE table_schema = 'ticket_system'
  AND column_name IN ('normalized_subject', 'message_id')
ORDER BY table_name, index_name;

SELECT table_name, index_name, ROUND(SUM(stat_value) * @@innodb_page_size / 1024 / 1024, 1) AS index_mb
FROM mysql.innodb_index_stats
WHERE database_name = 'ticket_system' AND stat_name = 'size'
GROUP BY table_name, index_name ORDER BY index_mb DESC LIMIT 10;
```

### B.5 备份与恢复的字符集陷阱

- `mariadb-dump` 与导入端都必须指定 `--default-character-set=utf8mb4`（`scripts/backup.sh` / `restore.sh` 已固定）。
- 一端 utf8mb4、另一端 latin1 会造成"中文变问号"或二次编码（`é` 变 `Ã©` 这类）。
- 二进制列（`mailboxes.secret_encrypted`）用 `--hex-blob` 导出，避免随字符集被改写。
- 导入前先确认会话字符集：
  ```sql
  SELECT @@character_set_client, @@character_set_connection, @@character_set_results;
  ```

### B.6 其他

| 事项 | 说明 |
|---|---|
| 全文检索 | Django 的全文检索绑定 PostgreSQL，MariaDB 上不可用；MVP 用 `LIKE`，量大再考虑原生 `MATCH...AGAINST` |
| 排序规则一致性 | 库/表/连接三者一致（本环境统一 utf8mb4_unicode_ci），跨库 JOIN 才不会有隐式转换 |
| 大邮件 | 默认 `max_allowed_packet` 16 MB，`body_html` 为 `TEXT`（上限 64 KB），正常邮件无压力；若出现超大正文报错需评估 |
| 迁移与备份顺序 | 迁移属于 DDL，会被 `--single-transaction` 快照排除，请勿与备份并发 |
