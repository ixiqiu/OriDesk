## 3. 与文档伪代码的偏差（DEV-*）

### DEV-1 收件邮箱的类型判定（新增推断）

文档模型没有"统一邮箱"标志位。根据 §2.2 表格（"发到统一邮箱 → 按主题路由"、"发到组邮箱 → 直接进入该组"）
推导出判定规则并集中在 `entry_kind()`：

- 邮箱绑定了组（反向 OneToOne `mailbox.group` 存在）→ 组专用邮箱，来信直达该组；
- `is_fallback=True` → 全局兜底邮箱（也是无邮箱组的发信身份）；
- 其余 → 统一进线邮箱，走"粘性 → 规则 → 兜底组 → 管理员组"。

### DEV-2 `should_auto_reply` 的入参与求值时机（修正文档伪代码）

§6.5 伪代码在建单**之后**才调用 `should_auto_reply(ticket, sender)`，而 §5.3 的实现"若工单非空则返回 False"，
两者相乘会导致自动回复**永不触发**，与 §2.4 的语义和 §12.3 的用例直接冲突。
现在的实现是：

1. 先 `merged = find_ticket(...)`（归并结果，未归并为 `None`）；
2. 在新建工单**之前**调用 `should_auto_reply(merged, sender, now)`；
3. 建单/归并、落库、打待回复标签；
4. 首次进线才发送自动回复。

### DEV-3 附件解析与落盘的先后顺序

§6.5 伪代码在建单前就 `extract_attachments(msg)`，但 §6.3 要求路径含 `ticket_id`。
实现为：`parser.extract_attachments()` 返回**内存态**附件 → 建单建消息后由
`pipeline._persist_attachments()` 按 `media/attachments/{ticket_id}/{message_id}/{filename}` 落盘。

### DEV-4 MariaDB 不支持带条件的唯一约束（重要）

`UniqueConstraint(fields=["is_fallback"], condition=Q(is_fallback=True))` 与
`UniqueConstraint(fields=["scope","group"])` 在 MariaDB/MySQL 上**不会被创建**：
Django 的 `schema.py::_unique_supported()` 在 `supports_partial_indexes=False` 时返回 `False`，
`_create_unique_sql()` 随即返回 `None`（静默跳过，不报错）。
因此除保留文档要求的约束外，另加**等价的模型层校验**：

- `Mailbox._assert_fallback_unique()`（`clean()` + `save()`）；
- `Template.save()` 中"全局模板只能一套"的校验；
- 唯一性语义在 SQLite/PostgreSQL 上仍由数据库约束保证。

### DEV-5 IMAP 位点推进更保守

§6.4 伪代码在处理循环后无条件 `mailbox.last_uid = max(uids)`，一旦某封邮件处理失败就会被永久跳过。
实现只把位点推进到**连续成功处理**的最后一封，失败即停，下一轮重试。
另外增加 `Message-ID` 幂等去重（`pipeline.already_seen`），防止 IMAP 重投或 UIDVALIDITY 变化后重复建单。

### DEV-6 `Mailbox` 模型归属

§4.1 把"邮箱配置"描述在 `mailboxes` app，但 §4.2 的代码把 `Mailbox` 定义在 `apps/accounts/models.py`，
且 `Ticket/Message` 的外键写死 `"accounts.Mailbox"`。实现遵循**代码**：模型在 `accounts`，
`mailboxes` app 只承载解析、净化、过滤、同步、发信、流水线。

### DEV-7 `resolve_template(mailbox)` 的反向 OneToOne 陷阱

文档写法 `if mailbox.group:` 在邮箱未绑定组时会抛 `RelatedObjectDoesNotExist`
（它同时继承 `AttributeError`），导致自动回复直接失败。实现统一用
`getattr(mailbox, "owning_group", None)`（见 `Mailbox.owning_group`）。

### DEV-8 `add_tag` 动作的落库载体（v1.2 经人工确认新增模型）

§4.4 的 `ACTION_TYPE_CHOICES` 含 `add_tag`，但 §4.3 的模型没有标签字段，规则命中后无处落库。
文档 §10.4 规定「禁止 AI 自行修改 Model 字段，需人工确认」，因此第一版只把标签写进审计留痕。
**人工确认后（v1.2）新增两个模型**：

- `Tag`（`db_table=tags`）：`name`、`group`（为空=全局标签，否则组专属）、`color`、`description`、`is_active`；
  约束：组作用域内同名唯一（数据库唯一约束 + 模型层 `clean()/save()` 兜底「全局标签」——
  SQL 中 NULL 互不相等，与 `Mailbox` 兜底邮箱同一处理方式）。
- `TicketTag`（`db_table=ticket_tags`）：`ticket`、`tag`、`added_by`、`source`（rule/manual）、`created_at`；
  约束：同一工单同一标签唯一。

配套实现：`apps/tickets/services.py` 的 `resolve_tag/add_tag/remove_tag/tags_available_for/ticket_tag_names`；
规则动作在 `apps/routing/services.apply_rule_actions()` 中真正落库（`source="rule"`，与 `set_status`/`assign_user`
共享一条 `rule_action` 审计）；界面上工单详情可增删标签、收件箱可按标签筛选、`/routing/tags/` 可维护标签字典。

测试：`tests/test_tags.py`（模型不变量与服务）、`tests/test_tag_views.py`（界面与权限）。

### DEV-19 测试模式会关闭 HTTPS 强制跳转（生产严禁 DJANGO_TESTING）

`config/settings.py` 里生产安全开关（`SECURE_SSL_REDIRECT`、`SESSION_COOKIE_SECURE`、
`CSRF_COOKIE_SECURE`、HSTS）挂在 `not DEBUG` 分支上。但单元测试通过 Django test client 走
`http://testserver`，若沿用生产开关，每个请求会先被 301 到 https，导致"未登录跳 302 / 越权 403"
这类断言全部失配（GitHub CI 首跑真实踩到）。因此 `UNDER_TEST`（pytest 加载或 `DJANGO_TESTING=1`）时
显式关闭这些开关。

副作用是：如果有人把 `DJANGO_TESTING=1` 带进生产 `.env`，安全开关会被**静默**关闭，
而 `DEBUG=False` 的常规检查发现不了。为此 `manage.py deploy_check` 单列一项判 FAIL
（`tests/test_deploy_check.py` 覆盖），部署手册 §1 第 18 项与 §3.1 也已列入检查清单。

### DEV-18 邮箱接入与"飞书"解耦（服务商中立 + 图形化配置）

§2.1 的表述是"所有邮箱通过 SMTP/IMAP 连接飞书企业邮箱"，容易被读成"系统只支持飞书"。
实现上接入层**只依赖标准协议**，与具体服务商无关：

- `apps/mailboxes/imap_client.py::connect_imap()` 统一"建连 → 加密 → 登录"，`sync.py` 与后台的
  "连通性检查"共用同一条路径（避免"检查通过但同步失败"）；
- `imap_ssl/smtp_ssl` 两个开关表达两类安全连接：勾选=隐式 TLS（993/465）；
  不勾选=明文连接后**强制 STARTTLS**（143/587），服务器不支持时直接报错，**不退回明文登录**；
- `apps/accounts/provider_presets.py` 提供 10 个服务商预设（飞书只是其中之一）+ 自定义，
  界面上"选预设 → 自动填主机/端口/加密"，并给出该服务商的授权码获取提示；
  无脚本环境也能在保存阶段由 `MailboxForm.clean()` 服务端兜底填充；
- 端到端限制见 `docs/邮箱接入指南.md` §8（例如 Microsoft 365 的 OAuth2 需要新增字段与授权流程，
  属 §10.4 需人工确认的变更）。

测试：`tests/test_mailbox_connection.py`（预设数据一致性、SSL/STARTTLS 策略、明文拒绝、
连通性检查不 500 且不发信、界面只选预设即可保存、文档漂移守卫、"代码里无飞书专属逻辑"守卫）。

### DEV-17 不能解析归属组的规则不阻断路由

`add_tag` / `set_status` 这类动作不决定归属组。若某条优先级最高的规则命中了但 `resolve_group()` 返回 `None`，
路由引擎会**继续尝试下一条规则**（记 `WARNING`），而不是直接失败——否则「只打标签」的规则会导致所有来信无法建单。
组路由仍满足 §2.2 的「第一个能确定归属组的规则命中即停」。

### DEV-9 改派时清空认领人

文档只说"原组默认失去可见性"。实现额外清空 `assignee`（并在审计里记录原认领人），
否则原组人员会通过认领关系继续持有工单，与"原组失去可见性"矛盾。

### DEV-10 自动回复不清除"待回复"标签

§5.3 的伪代码没有改标签，§2.6 也说"有人回复才消失"。因此自动回复只写消息，
只有 `send_reply`（人工外发）才把 `is_awaiting_reply` 置为 `False`。

### DEV-11 索引长度提示的核对结论（§8.1）

`utf8mb4` 下 `CharField(max_length=500)` 的索引键为 2000 字节，MariaDB 10.11 默认
`ROW_FORMAT=DYNAMIC` + `innodb_large_prefix=ON` 支持 3072 字节键长，因此
`tickets.normalized_subject`、`messages.message_id` 的索引可以保留 500 长度，无需截断为 191。

### DEV-12 规则匹配必须解码 RFC2047 邮件头

`msg.get("Subject")` 在 compat32 策略下返回的是编码后的原始串（`=?utf-8?b?...?=`）。
`Rule._candidates()` 先做 MIME 头解码再匹配，否则中文规则永远无法命中（已由
`test_sticky_within_window` 等用例回归保护）。

### DEV-13 每日一次的解析开销

`pipeline.process_inbound` 先 `parse_mime()`（供防循环/归并/规则使用）再 `parse_inbound()`
（供正文与附件使用），对大附件邮件存在一次重复解析。这是为了保持
`filters`/`find_ticket`/`Rule.matches` 都直接接收 `email.message.Message` 的文档接口形态；
在 MVP 规模下开销可忽略，已在此记录以便后续优化。

### DEV-14 附件下发改为"鉴权 + X-Accel-Redirect"（安全加固）

文档 §9.2 的 Nginx 示例把 `/media/` 直接交 Nginx 服务，这会让工单附件绕过应用层的可见性校验
（路径含自增 `ticket_id`，可枚举）。实现做了两层加固：

- `apps/tickets/views.py::_serve_attachment` 先完成登录 + 工单可见性校验；配置了
  `ATTACHMENT_X_ACCEL_PREFIX`（如 `/media/attachments/`）时返回
  `X-Accel-Redirect`（路径做百分号编码，保证头部 ASCII 安全），由 Nginx 的 `internal`
  location 传输文件；未配置时由 Django 流式返回（本地开发可用）。
- `deploy/nginx/ticket.example.com.conf` 中 `/media/attachments/` 默认 `internal;`，
  匿名直链一律 404；`.env.example` 默认给出 `ATTACHMENT_X_ACCEL_PREFIX=/media/attachments/`。

测试：`tests/test_ticket_views.py::test_attachment_download_uses_x_accel_when_configured`
与 `test_attachment_download_x_accel_still_enforces_visibility`。

### DEV-15 附件在线预览收敛为类型白名单（安全加固）

§6.3 只列举了"危险扩展名（.exe/.bat/.js/.scr/.vbs）不可预览"。仅靠这份列表不够：
`text/html`、`image/svg+xml`、`application/xhtml+xml` 等**活动内容**若按发送方声明的 MIME 内联返回，
就会在应用同源执行脚本（存储型 XSS；由独立验证发现）。实现把"可预览"从"黑名单排除"改为**白名单**：

- 可内联：`image/png|jpeg|gif|webp|bmp`、`text/plain`、`application/pdf`；
- 其余（含 HTML/SVG/XHTML/XML/未知类型）一律 403，只能下载；
- 预览响应用白名单 MIME + `X-Content-Type-Options: nosniff` +
  `Content-Security-Policy: default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; sandbox`；
- 文件名先做规范化（剥离控制字符与尾部空格/点），否则 `tool.exe.` 可绕过危险扩展名判断。

测试：`tests/test_attachment_security.py`（42 例）。

### DEV-16 粘性窗口仅在 N>0 时启用

§2.3 以 `last_message_at >= now - N 天` 判定粘性（含等号，边界算窗口内）。
当管理员把 `sticky_window_days` 设为 0（本意是"关闭粘性"）时，`last_message_at == now` 仍满足 `>=`，
会误判为粘性。实现改为**仅当 N > 0 时启用粘性**，边界语义（含等号）保持不变并有用例固定。
