# 运维手册 · 新技元邮箱及工单管理系统（OriDesk）

面向日常值班与应急处置。所有命令可直接复制执行，路径按实际部署替换（本文以 `/opt/OriDesk` 为项目目录、`/srv/ticket-system` 为数据目录、`ticket.example.com` 为示例域名）。

- 部署、升级、备份恢复的具体步骤见 [部署手册](部署手册.md)。
- 本系统的外部依赖是**飞书企业邮箱的 IMAP/SMTP**：绝大多数"系统故障"实际是邮箱侧授权、配额或服务端状态变化引起的，排障时先看邮箱侧。

## 1. 值班准备：一次性配置

把下面这段加到运维机（有 Docker 权限、能访问项目目录）的 `~/.bashrc`，后续所有 SQL/Redis 命令都用这几个封装，避免每次敲一长串引号：

```bash
# 项目目录（按实际部署调整）
export ORIDESK_DIR=/opt/OriDesk

# 容器操作
oridesk() { docker compose -f "$ORIDESK_DIR/docker-compose.yml" "$@"; }

# 应用库 SQL（用应用账号，读多写少；支持 -e "SQL" 或 stdin 重定向）
oridesk_sql() {
  docker compose -f "$ORIDESK_DIR/docker-compose.yml" exec -T db \
    sh -c 'MYSQL_PWD="$MARIADB_PASSWORD" mariadb --default-character-set=utf8mb4 -u"$MARIADB_USER" "$MARIADB_DATABASE" "$@"' sh "$@"
}

# 管理库 SQL（需要查 information_schema、看全局状态时用 root）
oridesk_sql_root() {
  docker compose -f "$ORIDESK_DIR/docker-compose.yml" exec -T db \
    sh -c 'MYSQL_PWD="$MARIADB_ROOT_PASSWORD" mariadb --default-character-set=utf8mb4 -uroot "$@"' sh "$@"
}

# Redis / RQ
oridesk_redis() { docker compose -f "$ORIDESK_DIR/docker-compose.yml" exec -T redis redis-cli "$@"; }
oridesk_rq()    { docker compose -f "$ORIDESK_DIR/docker-compose.yml" exec -T worker sh -c 'rq "$@"' sh "$@"; }
```

```bash
source ~/.bashrc
oridesk_sql -e "SELECT 1"        # 验证封装可用
```

需要交互式 SQL 时（`-T` 不分配终端，不适合交互）：

```bash
docker compose -f "$ORIDESK_DIR/docker-compose.yml" exec db \
  sh -c 'MYSQL_PWD="$MARIADB_PASSWORD" mariadb --default-character-set=utf8mb4 -u"$MARIADB_USER" "$MARIADB_DATABASE"'
```

### 1.1 巡检用到的 Redis 键（RQ 2.x 约定）

| 键 | 类型 | 含义 |
|---|---|---|
| `rq:queue:default` | list | 通用队列待处理任务数（`LLEN`） |
| `rq:queue:mail` | list | 邮件队列待处理任务数（`LLEN`） |
| `rq:registry:default` / `rq:registry:mail` | zset | 正在执行的任务（`ZCARD`） |
| `rq:failed:default` / `rq:failed:mail` | zset | 失败任务（`ZCARD`） |
| `rq:workers` | set | 已注册 worker（`SMEMBERS`） |
| `rq:worker:<id>` | hash | 单个 worker 的信息与心跳（`TTL` 正数=存活） |
| `rq:queues` | set | 已知队列名 |

对应关系：`config/settings.py` 中 `RQ_QUEUES = {"default": …, "mail": …}`，worker 用 `python manage.py rqworker default mail` 同时消费两个队列。

### 2.2 服务与健康

```bash
oridesk ps
oridesk ps --format 'table {{.Service}}\t{{.Status}}'
curl -fsS https://ticket.example.com/healthz ; echo
curl -fsS http://127.0.0.1:8000/healthz ; echo     # 绕过 Nginx 直连后端
```

判定：

| 现象 | 含义 |
|---|---|
| web `healthy`、直连后端 200 | Web 与数据库正常 |
| web `healthy` 但 `https://` 502 | Nginx → 8000 链路问题（Nginx 未 reload、端口/upstream 不一致） |
| web `unhealthy` 且 healthz 503 | 数据库不可达：查 `oridesk logs db`、`oridesk ps db` |
| worker/scheduler `unhealthy` | 分别代表"worker 心跳丢失"与"数据库连接失败" |

### 2.3 IMAP 同步状态

**首选：看调度器日志**（同步进度、失败、防循环丢弃都在这里）：

```bash
oridesk logs --tail=200 scheduler
oridesk logs --since=1h scheduler | grep -E "轮询开始|轮询结束|同步完成|同步失败|UIDVALIDITY|防循环|处理失败"
```

正常的一轮长这样（每个启用邮箱一行汇总）：

```text
IMAP 轮询开始：2026-02-18T02:30:00+00:00
邮箱 support@example.com 同步完成：拉取 12，入库 10，跳过 2，失败 0
IMAP 轮询结束：3 个邮箱，入库 10 封，耗时 4.2s
```

**辅助：看数据库里的同步位点**（用于确认位点是否在推进、UIDVALIDITY 是否被重置）：

```bash
oridesk_sql -e "
SELECT m.id, m.email, m.is_active, m.last_uid, m.uidvalidity,
       (SELECT MAX(msg.created_at) FROM messages msg
         WHERE msg.mailbox_id = m.id AND msg.direction = 'in') AS last_inbound_at,
       (SELECT COUNT(*) FROM messages msg
         WHERE msg.mailbox_id = m.id AND msg.direction = 'in'
           AND msg.created_at >= NOW() - INTERVAL 1 DAY) AS inbound_24h
FROM mailboxes m ORDER BY m.id"
```

判读要点：

- **没有来信的邮箱，`last_inbound_at` 本来就不会更新**，不能只看这个时间判断"同步坏了"；应结合"调度器每轮都有 `轮询开始/结束` 日志"与 `last_uid` 是否随来信增长。
- `is_active = 0` 的邮箱不会被轮询（`sync_all_mailboxes` 只遍历启用邮箱），这是刻意冻结，不是故障。
- `last_uid` 突然变小 → 说明发生过 `UIDVALIDITY` 重置（§3.2）。

**手工触发一轮同步**（排查时用；务必先停掉正在跑的调度器，避免两个进程并发同步同一邮箱）：

```bash
oridesk stop scheduler
oridesk run --rm scheduler python manage.py runapscheduler --once
oridesk up -d scheduler
```

### 2.4 队列与 worker

```bash
oridesk_redis LLEN rq:queue:mail
oridesk_redis LLEN rq:queue:default
oridesk_redis ZCARD rq:registry:mail          # 正在执行
oridesk_redis ZCARD rq:failed:mail            # 失败任务
oridesk_redis ZCARD rq:failed:default
oridesk_redis SMEMBERS rq:workers             # 已注册 worker
oridesk_redis --scan --pattern 'rq:worker:*'  # 单个 worker 键
oridesk_rq info --url "$(oridesk exec -T worker printenv REDIS_URL | tr -d '\r')"
```

worker 心跳：对 `rq:worker:<id>` 逐个查 `TTL`，正数表示存活（RQ 默认 `worker_ttl=420`，续期后 TTL 约 480 秒）。

```bash
for k in $(oridesk_redis --scan --pattern 'rq:worker:*' | tr -d '\r'); do
  echo "$k TTL=$(oridesk_redis TTL "$k" | tr -d '\r')"
done
```

**重要区分**：容器 `healthy` 只代表"至少有一个 worker 在注册心跳"，**不代表队列不积压**。积压必须单独看 `LLEN`。

### 2.5 出站流量与自动回复（风暴预警）

```bash
# 近 6 小时按小时统计出站/自动回复
oridesk_sql -e "
SELECT DATE_FORMAT(created_at, '%Y-%m-%d %H:00') AS hour,
       COUNT(*) AS out_total,
       SUM(is_auto_reply) AS auto_total
FROM messages
WHERE direction = 'out' AND created_at >= NOW() - INTERVAL 6 HOUR
GROUP BY hour ORDER BY hour"

# 近 1 小时收到最多自动回复的收件人（异常的循环特征）
oridesk_sql -e "
SELECT to_addr, COUNT(*) AS auto_cnt
FROM messages
WHERE is_auto_reply = 1 AND created_at >= NOW() - INTERVAL 1 HOUR
GROUP BY to_addr ORDER BY auto_cnt DESC LIMIT 10"

# 近 1 小时新建工单最多的客户（批量/风暴特征）
oridesk_sql -e "
SELECT customer_email, COUNT(*) AS cnt
FROM tickets WHERE created_at >= NOW() - INTERVAL 1 HOUR
GROUP BY customer_email ORDER BY cnt DESC LIMIT 10"

# 审计动作分布
oridesk_sql -e "
SELECT action, COUNT(*) AS cnt FROM audit_logs
WHERE created_at >= NOW() - INTERVAL 1 HOUR GROUP BY action ORDER BY cnt DESC"
```

参考阈值（需按实际业务量校准，首次上线一周后回填基线）：单小时出站 > 200 封、自动回复占比 > 80%、同一客户 1 小时内新建工单 > 20、单邮箱 1 小时内新建工单 > 200 —— 任一命中即按 §3.3 预案介入。

### 2.7 数据库巡检

```bash
# 库/表字符集（第二条应为空）
oridesk_sql_root -e "
SELECT DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
FROM information_schema.SCHEMATA WHERE SCHEMA_NAME = DATABASE();
SELECT table_name, table_collation FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_collation NOT LIKE 'utf8mb4%';"

# 体积与行数（快速掌握增长）
oridesk_sql -e "
SELECT table_name, table_rows,
       ROUND((data_length + index_length)/1024/1024, 1) AS mb
FROM information_schema.tables WHERE table_schema = DATABASE()
ORDER BY (data_length + index_length) DESC LIMIT 12;"

# 连接数与线程（排查连接泄漏）
oridesk_sql_root -e "
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
SELECT COUNT(*) AS processlist FROM information_schema.processlist;"

# 严格模式
oridesk_sql -e "SELECT @@sql_mode"
```

判读：

| 项 | 正常 | 异常处置 |
|---|---|---|
| 字符集 | 全部 `utf8mb4_*` | 部署手册附录 B.1 |
| `tickets` / `messages` 体积 | 平稳增长 | 突增查 §2.5 风暴指标 |
| `Threads_connected` | 与容器数同量级（个位数～几十） | 持续升高且不回落 → 检查是否有未释放连接/异常重试 |
| `sql_mode` | 含 `STRICT_TRANS_TABLES` | 检查 compose 的 db `command` 与连接 `init_options` |

### 2.8 业务不变量巡检

这几条不受数据库约束保护，必须靠巡检（原因见部署手册附录 B.3）。

```bash
# 1) 全局兜底邮箱必须 ≤ 1 行
oridesk_sql -e "SELECT id, email, is_fallback, is_active FROM mailboxes WHERE is_fallback = 1"

# 2) 兜底邮箱必须启用（无邮箱组发信依赖它）
oridesk_sql -e "SELECT id, email FROM mailboxes WHERE is_fallback = 1 AND is_active = 0"

# 3) 每个启用邮箱必须已配置凭据（密文非空）
oridesk_sql -e "SELECT id, email FROM mailboxes WHERE is_active = 1 AND (secret_encrypted IS NULL OR LENGTH(secret_encrypted) = 0)"

# 4) 外发消息必须能定位到实际发件人（自动回复除外）
oridesk_sql -e "
SELECT COUNT(*) AS out_without_sender FROM messages
WHERE direction = 'out' AND is_auto_reply = 0 AND actual_sender_id IS NULL"

# 5) 待回复标签与最后一条消息方向是否自洽（客户来信应为 1）
oridesk_sql -e "
SELECT t.id, t.is_awaiting_reply, m.direction, m.created_at
FROM tickets t
JOIN messages m ON m.id = (SELECT MAX(id) FROM messages WHERE ticket_id = t.id)
WHERE t.status <> 'closed' AND m.direction = 'in' AND t.is_awaiting_reply = 0
ORDER BY t.id DESC LIMIT 20"

# 6) 附件记录与磁盘文件一致性
oridesk_sql -N -B -e "SELECT path FROM attachments" | tr -d '\r' | sort > /tmp/oridesk_db_paths.txt
find /srv/ticket-system/media -type f -printf '%P\n' | sort > /tmp/oridesk_fs_paths.txt
echo "--- DB 有记录但文件缺失（需告警）---"; comm -13 /tmp/oridesk_fs_paths.txt /tmp/oridesk_db_paths.txt | head
echo "--- 磁盘有文件但无 DB 记录（孤儿文件）---"; comm -23 /tmp/oridesk_fs_paths.txt /tmp/oridesk_db_paths.txt | head
```

异常处理：

| 异常 | 处理 |
|---|---|
| 兜底邮箱 > 1 行 | 人工保留一个（与 `settings.fallback_mailbox_id` 一致的那一个），其余 `UPDATE mailboxes SET is_fallback = 0 WHERE id = …`；改完重跑第 1 条确认 |
| 兜底邮箱被停用 | 置回 `is_active = 1`（应用层 `save()` 也会强制启用，直接改库需手工修正） |
| 启用邮箱缺凭据 | 在管理后台重新录入授权码（`set_secret()` 加密存储） |
| 文件缺失 | 从最近一次 `ticket-media-*.tar.gz` 定点取回（部署手册 §7.6）；无法找回时告知业务方并保留记录 |
| 孤儿文件 | 确认无 DB 记录后移入 `/srv/ticket-system/media/_orphan/` 观察一周再删，避免误删 |

## 3. 常见故障处置

### 3.1 邮箱授权码失效

**表现**：工单不再新增；`scheduler` 日志出现

```text
邮箱 xxx@example.com 同步失败：邮箱 xxx@example.com 凭据不可用：…
```

（`MailSyncError: 邮箱 … 凭据不可用` 来自 `apps/mailboxes/sync.py`，底层是 IMAP `AUTHENTICATIONFAILED`/`LOGIN failed`。该邮箱不会出现 `同步完成` 汇总行，其余正常邮箱仍会照常输出。）

**常见原因**：飞书后台改过密码；授权码被撤销或过期；邮箱被停用；开启了"仅允许客户端专用密码"但用的是登录密码；账号被风控锁定。

**处置**：

1. 确认影响范围（哪些邮箱、多久）：
   ```bash
   oridesk logs --since=24h scheduler | grep -c "凭据不可用"
   oridesk logs --since=24h scheduler | grep "凭据不可用" | tail -5
   ```
2. 到飞书企业邮箱后台为受影响账号重新生成授权码（IMAP/SMTP 客户端专用密码）。
3. 在管理后台（`/admin/` → 邮箱）更新该邮箱授权码；应用层会用 `FERNET_KEY` 加密写入。
4. **同步位点不会丢**：`last_uid` 保持不动，恢复后从该位点继续补拉，故障期间的来信不会丢（前提是邮件仍在服务端 INBOX）。
5. 验证：
   ```bash
   oridesk stop scheduler
   oridesk run --rm scheduler python manage.py runapscheduler --once
   oridesk up -d scheduler
   # 期望出现：邮箱 xxx 同步完成：拉取 N，入库 M，跳过 K，失败 0
   ```
6. 若飞书后台显示"已发送邮件数/登录异常"告警，一并记录到值班日志。

**预防**：授权码到期前主动轮换；把 `凭据不可用` 关键字加入日志告警；为每个邮箱保留一份"最近成功同步时间"基线。

### 3.2 UIDVALIDITY 变化

**背景**：IMAP 的 `UIDVALIDITY` 是邮箱"世代号"。服务端重建/迁移邮箱后该值会变，此时旧的 `UID` 全部失效。系统检测到变化会打警告并把 `last_uid` 归零（`apps/mailboxes/sync.py`）：

```text
邮箱 xxx@example.com 的 UIDVALIDITY 变化（1234567890 → 987654321），重置同步位点。
```

**影响**：位点归零后，系统会从头扫描 INBOX：

- 已入库且 `Message-ID` 相同的邮件不会重复入库（`already_seen` 幂等保护，日志 `的邮件已处理过，跳过。`）；
- **但被防循环过滤过的邮件、以及 Message-ID 缺失/被改写的邮件会被重新处理**，可能重新建单或重复触发自动回复（自动回复有 `auto_reply_already_sent` 兜底，同一工单不会重复发送）。

**处置**：

1. 先判断影响面：重置后一轮同步的拉取量。
   ```bash
   oridesk logs --since=6h scheduler | grep -E "UIDVALIDITY|轮询结束"
   ```
2. 若 INBOX 邮件量很大（数千封以上），先冻结该邮箱，避免一次性灌入：
   ```bash
   oridesk_sql -e "UPDATE mailboxes SET is_active = 0 WHERE email = 'xxx@example.com'"
   ```
3. 评估是否需要"跳过历史积压"：希望从当前时间点继续收信时，把位点直接推到服务端当前 UIDNEXT 前一个值（UIDNEXT 可通过一次 IMAP 会话查询，或先放开同步、观察日志中拉取到的最大 UID 后回填）：
   ```bash
   oridesk_sql -e "UPDATE mailboxes SET last_uid = <UIDNEXT-1>, uidvalidity = <当前值>, is_active = 1 WHERE email = 'xxx@example.com'"
   ```
   注意：这样做会**跳过**中间的邮件（等于放弃补拉），需业务方确认。
4. 若已产生重复工单，按工单号/客户 + 时间窗口人工合并：把重复工单的 `messages` 归并到保留工单（`UPDATE messages SET ticket_id = <保留工单> WHERE ticket_id = <重复工单>`），再删除空壳工单（`DELETE FROM tickets WHERE id = <重复工单>`），并在审计中留说明。
5. 记录事件：UIDVALIDITY 变化属于邮箱服务端变更，应向邮箱管理员确认是否为迁移/清理所致。

**预防**：把 `UIDVALIDITY 变化` 设为高优先级日志告警；邮箱服务端变更前通知系统侧。

### 3.3 邮件风暴防护

**什么是风暴**：系统与外部（或系统自身）互相自动回信形成循环，短时间内产生大量出站邮件与工单，可能触发邮箱服务商限流甚至封禁。

**系统已有的防护**（`apps/mailboxes/filters.py`）：

| 规则 | 拦截对象 |
|---|---|
| `Auto-Submitted: auto-generated\|auto-replied` | 自动回复、自动生成通知 |
| `X-Auto-Response-Suppress: all` | 明确要求不自动回复的邮件 |
| `Precedence: bulk\|junk\|list` | 批量/列表邮件 |
| `List-Id` 存在 | 邮件列表 |
| 发件人是本系统任一邮箱地址 | 自己发出去又绕回来 |
| 发件人匹配 `^(no-?reply\|mailer-daemon\|postmaster)@` | 系统退信与通知 |

同时，系统发出的自动回复带 `Auto-Submitted: auto-replied`，形成对称防护（`apps/autoresponder/services.py`）。命中拦截会记日志：

```text
邮箱 xxx@example.com UID=12345 命中防循环规则（auto-submitted），已丢弃。
```

**预警信号**（任一命中即按预案处置）：

| 信号 | 检查命令 | 阈值（示例基线，按业务校准） |
|---|---|---|
| 出站邮件突增 | §2.5 第一条 SQL | > 200 封/小时 |
| 自动回复占比过高 | §2.5 第一条 SQL | > 80% |
| 同一客户被反复回复 | §2.5 第二条 SQL | 同一收件人 > 20 封/小时 |
| 工单暴增 | §2.5 第三条 SQL | > 200 个/小时，或同一客户 > 20 个/小时 |
| 防循环拦截激增 | `oridesk logs --since=10m scheduler \| grep -c 防循环` | > 50 条/10 分钟 |
| 队列积压 | `oridesk_redis LLEN rq:queue:mail` | > 100 且持续增长 |

**应急处置（按顺序，先止血再定位）**：

```bash
# 1) 停止收信与队列消费 —— 最有效的一步
oridesk stop scheduler worker

# 2) 需要保留 worker 处理其他任务时，改为软暂停（worker 不再取新任务）
oridesk_rq suspend --url "$(oridesk exec -T worker printenv REDIS_URL | tr -d '\r')"
#    恢复：oridesk_rq resume --url "$(oridesk exec -T worker printenv REDIS_URL | tr -d '\r')"

# 3) 冻结可疑入口邮箱（所有邮箱：WHERE 1=1 会全部冻结，慎用）
oridesk_sql -e "UPDATE mailboxes SET is_active = 0 WHERE email = 'xxx@example.com'"

# 4) 观察队列与出站
oridesk_redis LLEN rq:queue:mail
oridesk_sql -e "SELECT COUNT(*) FROM messages WHERE direction='out' AND created_at >= NOW() - INTERVAL 30 MINUTE"
```

若停止上述进程后**仍有外发**，说明 Redis 曾不可用导致任务降级为同步执行（`apps/mailboxes/tasks.py::dispatch`，日志 `RQ 不可用（…），改为同步执行 …`），此时只能从邮箱侧止血：

- 在飞书后台**撤销该邮箱的 SMTP 授权码**（会让收信同时失效，属于彻底止血）；
- 或在宿主防火墙临时阻断到邮箱 SMTP 端口的出站流量（`iptables`/安全组），止血后立即恢复。

**定位与清理**：

```bash
# 找出风暴中心：谁在发、发给谁、是不是自动回复
oridesk_sql -e "
SELECT DATE_FORMAT(created_at,'%H:%i') AS t, from_addr, to_addr, is_auto_reply, COUNT(*) c
FROM messages WHERE direction='out' AND created_at >= NOW() - INTERVAL 2 HOUR
GROUP BY t, from_addr, to_addr, is_auto_reply ORDER BY c DESC LIMIT 20"

# 触发源邮件（是不是被漏过的自动邮件）
oridesk logs --since=2h scheduler | grep -B2 -A2 "命中防循环" | head -50

# 处理队列：确认任务内容后再决定丢弃
oridesk_rq info --url "$(oridesk exec -T worker printenv REDIS_URL | tr -d '\r')"
# 清空队列是破坏性操作，仅在明确知道任务内容且业务同意后执行：
# oridesk_rq empty --url "$(oridesk exec -T worker printenv REDIS_URL | tr -d '\r')" mail
```

**恢复与复盘**：

1. 修复触发源（补齐过滤规则、修模板、修循环逻辑），确认单封测试邮件全链路正常。
2. 逐个邮箱解冻，先只放开一个观察 10 分钟：
   `oridesk_sql -e "UPDATE mailboxes SET is_active = 1 WHERE email = 'xxx@example.com'"`
3. `oridesk up -d scheduler worker`，盯 `LLEN` 与出站量 30 分钟。
4. 复盘必须回答：哪封邮件触发的、哪条过滤规则没拦住、为什么自动回复没被 `auto_reply_already_sent` 拦住、监控为什么没提前告警。
5. 向受影响客户致歉（如已产生误发）。

**注意**：当前版本**没有"关闭自动回复"的配置开关**——`resolve_template_body()` 在找不到模板时会回退到内置 `DEFAULT_TEMPLATE`，所以"清空模板"并不能停发自动回复。应急停发的可用手段只有：冻结入口邮箱、停止 `worker`/`scheduler`、或撤销邮箱 SMTP 授权码。建议后续迭代增加"自动回复总开关"（记入需求池）。

### 3.4 队列 worker 掉线 / 队列积压

**表现**：`LLEN rq:queue:mail` 持续增长；`SMEMBERS rq:workers` 为空；`worker` 容器 `unhealthy`；界面上"回复"操作后邮件迟迟不发出。

**排查**：

```bash
oridesk ps worker
oridesk logs --tail=200 worker
oridesk_redis SMEMBERS rq:workers
oridesk_redis LLEN rq:queue:mail
oridesk_redis ZCARD rq:registry:mail          # 有值说明卡在某个任务上
oridesk_redis ZCARD rq:failed:mail            # 失败任务
docker stats --no-stream oridesk-worker       # 是否 OOM / CPU 打满
```

**常见原因与处置**：

| 原因 | 特征 | 处置 |
|---|---|---|
| 容器被杀（OOM） | `docker inspect oridesk-worker --format '{{.State.OOMKilled}}'` 为 true | 提高内存限制/排查附件内存占用；`oridesk up -d worker` |
| 单个任务超长 | `rq:registry:mail` 有值、日志停在某任务 | 任务默认超时 600 秒（`RQ_QUEUES.DEFAULT_TIMEOUT`）；超时后进入 failed 注册表，必要时重放 |
| worker 进程崩溃 | 日志末尾有 Traceback | 修 bug；`oridesk restart worker` |
| Redis 不可达 | 日志 `RQ 不可用（…），改为同步执行` | 先修 Redis（`oridesk ps redis`、`redis-cli ping`），再重启 worker |
| 队列名不匹配 | 任务入到别的队列 | 确认 worker 启动命令包含 `default mail` |

**恢复与重放**：

```bash
oridesk restart worker
# 观察是否开始消费
oridesk_redis LLEN rq:queue:mail

# 重放失败任务（确认原因已修复后再做，避免重复发信）
oridesk_rq requeue --url "$(oridesk exec -T worker printenv REDIS_URL | tr -d '\r')" --queue mail --all
```

**重要**：`requeue --all` 会让失败的发信任务重跑，**可能重复发信**。执行前先看 failed 注册表里的任务内容，必要时只重放指定 job id。

```bash
# 查看失败任务的 job id 与内容（json 序列化，便于人读）
oridesk_redis ZRANGE rq:failed:mail 0 -1
oridesk_rq info --url "$(oridesk exec -T worker printenv REDIS_URL | tr -d '\r')"
```

## 4. 应急处置流程

### 4.1 通用流程（五步）

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 止损 | 先让影响不再扩大：停 `worker`/`scheduler`、冻结邮箱、挂维护页（Nginx `return 503`） | 影响面停止增长 |
| 2 定位 | 收集证据：`oridesk ps`、`logs --since=1h`、队列深度、数据库状态、`df -h`；**不要重启前不留证据** | 时间线 + 关键日志 |
| 3 修复 | 按 §3 对应 runbook 处理；不确定时优先恢复到最近可用备份（部署手册 §7） | 故障消除 |
| 4 验证 | `/healthz` 200、一轮 `runapscheduler --once` 成功、测试收发一封邮件、队列回落 | 端到端可用 |
| 5 复盘 | 写明根因、影响范围、时间线、改进项与责任人 | 复盘记录（24 小时内） |

铁律：

- 动手前先备份：任何数据操作前跑一次 `sudo $ORIDESK_DIR/scripts/backup.sh`。
- 不要在生产用 `docker compose down -v`（会删除 `db_data`/`redis_data` 卷）。
- 不要在 `db`/`redis` 运行期间手工改卷内文件。
- 直连改库（`UPDATE`/`DELETE`）都会绕过应用层不变量与审计，改之前想清楚，改之后要核对（§2.8）。

### 4.2 场景：全站不可用（502/超时）

```bash
oridesk ps
oridesk logs --tail=200 web
curl -fsS http://127.0.0.1:8000/healthz ; echo
sudo tail -50 /var/log/nginx/ticket.example.com.error.log
df -h /srv
free -h
```

处置顺序：数据库（`db` 容器/磁盘/连接数）→ `web` 进程 → Nginx → 宿主资源。若是磁盘满，先释放空间（旧备份、`<media>.before-restore-*`、日志），再重启 `web`。恢复后必须验证收信链路（`runapscheduler --once`）。

### 4.3 场景：邮件不进单（但系统本身可用）

按链路逐段排除：

| 环节 | 检查 | 结论 |
|---|---|---|
| 邮件是否到达邮箱 | 飞书邮箱网页版看 INBOX | 没到 → 邮箱侧问题（网关/反垃圾） |
| 系统是否在轮询 | `oridesk logs --tail=50 scheduler` 有 `IMAP 轮询开始/结束` | 没有 → scheduler 故障（§3.4/部署手册 §9） |
| 邮箱是否被冻结 | §2.3 的 `is_active` 查询 | `is_active=0` → 确认是否为人为冻结 |
| 凭据是否有效 | 日志 `凭据不可用` | 有 → §3.1 |
| 是否被防循环丢弃 | 日志 `命中防循环规则` | 是 → 确认规则是否过宽（§3.3） |
| 是否解析/处理失败 | 日志 `处理失败，将在下一轮重试。` | 有 → 收集原始邮件做复现，位点不会推进（不会丢信） |
| 位点是否推进 | §2.3 的 `last_uid` 前后对比 | 不推进且无失败日志 → 检查 IMAP 搜索范围（UID 比较）与邮箱服务端行为 |
| 是否建单但未显示 | 用 `oridesk_sql -e "SELECT id,subject,group_id,created_at FROM tickets ORDER BY id DESC LIMIT 5"` 查最新工单 | 已建单 → 页面/可见性问题（组权限） |

### 4.4 场景：发信异常或误发

**发不出**：

```bash
oridesk logs --tail=200 worker | grep -iE "smtp|send|凭据|拒绝"
oridesk_sql -e "SELECT id, subject, to_addr, actual_sender_id, created_at FROM messages WHERE direction='out' ORDER BY id DESC LIMIT 10"
```

排查：授权码（§3.1）、邮箱 SMTP 端口/SSL 配置（`Mailbox.smtp_port`/`smtp_ssl`）、服务商限流（大量外发后常见，表现为连接被拒或延迟）、网络出站 465/587 是否被防火墙拦截。**注意**：`send_reply` 先发信后写库，若发信成功但写库失败，会出现"客户收到了但系统没记录"，此时不要重发，先核对邮箱"已发送"再人工补记。

**误发/发错对象**：立即停止 `worker`（避免队列里剩余任务继续发），核对 `messages` 中已发出的记录与 `audit_logs` 的 `reply` 记录，向业务方通报，并按需要向客户致歉。审计表记录了"谁、何时、以哪个组身份、给谁发了什么"（`audit_logs.detail`），是定位责任链的关键。

### 4.5 场景：数据误删/损坏

```bash
# 1) 立即停写，避免覆盖
oridesk stop web worker scheduler

# 2) 先做一次现状快照（保留现场）
sudo $ORIDESK_DIR/scripts/backup.sh

# 3) 查看可用备份
sudo $ORIDESK_DIR/scripts/restore.sh --list
```

- **只缺几条数据/几个附件**：按部署手册 §7.6 定点恢复，不要整套覆盖。
- **整库损坏**：按部署手册 §7.3 全套恢复，**恢复后必须做 §7.4 的 IMAP 位点核对**，否则会重复拉取备份点之后的邮件。

### 4.6 场景：安全事件

| 事件 | 立即动作 | 后续 |
|---|---|---|
| `.env` / `FERNET_KEY` 泄露 | 轮换 `DJANGO_SECRET_KEY`（所有会话失效）→ 在飞书后台重置**全部**邮箱授权码并在后台重录 → 轮换 `DB_PASSWORD`/`DB_ROOT_PASSWORD` → 更换 `FERNET_KEY` 需配合重录（旧密文不可解） | 检查 `audit_logs` 的 `login` 记录与 Nginx 访问日志异常 IP；评估邮件数据暴露范围并上报 |
| 附件被匿名下载（`/media/` 直出） | 立即在 Nginx 的 `/media/attachments/` 加 `internal;` 并 reload（会导致附件暂时 404，属预期）→ 联系开发实施方案 A | 检查访问日志中被访问的附件路径，评估暴露范围 |
| 异常登录 | 禁用可疑账号并强制改密；检查该账号在 `audit_logs` 的操作 | 复核组成员与管理员组配置 |
| 服务器被入侵 | 断网 → 保留镜像与日志 → 从干净备份重建（**不要**在被入侵机器上恢复后继续用） | 事后审计与加固 |
